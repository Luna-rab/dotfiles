# 文章作成ルール

ドキュメント・コードコメント・コミットメッセージ・PR 本文・返答など、あとに残る文章を書くときに従ってください。狙いは、書き手の前提を共有しない読者——数か月後の自分・新しく参加した人・会話の文脈を持たない AI——が、その文章だけで意味を理解できるようにすることです。

## 明示的なスタイル指定が優先する

書く対象に固有の書き方が明示的に指定されている場合は、このルールより**そちらを優先**してください。例として、Claude Code の skills（`SKILL.md`）は公式ガイド（https://code.claude.com/docs/ja/skills ）が「本体は簡潔に。実行内容を述べ、方法や理由を説明しない」と指示しているため、このルールの「理由（なぜ）を書く」より公式ガイドに従います。指定と矛盾しない範囲では、以下の項目（簡潔・文脈なしで読める）は引き続き適用してください。

## 原則

書き手が当たり前だと思っている前提は、読み手には無い。**文章だけで意味が通るように書いてください。** 書き終えたら「この文脈をまったく知らない読者が、これだけで理解できるか」を自問し、できないなら欠けている前提・定義・具体例を補ってください。

## 誰でも読めるように書く（文脈がなくても読める）

- そのプロジェクトやチームの事情を知らない人でも理解できるように書いてください。
- 略語・専門用語・記号は初出で定義してください（例:「SBC（状態基準チェック）」）。定義のない内部用語をそのまま使わない。
- 結論だけでなく理由（なぜ）を書いてください。判断は、根拠と、検討して退けた代替案も残す。
- 見出し・箇条書き・表で構造化してください。密な段落より、区切られた要点のほうが読み手は追いやすい。

## 悪い例 → 良い例

- 悪い:「上記の器に前倒しで載せ、二重化を避ける。」
  - 何の器か・何を前倒すのか・何が二重になるのかが読み手にわからない。
- 良い:「判定処理を関数 `check_targets` 1 つにまとめ、解決前チェックと自動判定（SBC = 状態基準チェックの 8 番）の両方から呼ぶ。どちらの経路も同じ行き先・同じイベントを使うので、結果が二重に数えられない。」
