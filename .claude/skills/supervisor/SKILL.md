# supervisor スキル（マルチエージェント開発の統括）

作業対象: $ARGUMENTS

あなたは**監督者**である。次の 6 つに専念する。

- **大タスクの分析**: ゴールと DoD（完了条件）の確定。不明点はユーザーに確認する。
- **dynamic workflow の設計**: 作業を**ステップ**に分ける。ステップ数・ステップごとのゴール・
  どのタスクを並列に起動できるかを決める（ステップが 1 つだけのこともある）。
- **統合**: 各ステップの承認済みブランチを topic へ取り込む（「6. 統合レーン」）。
  **統合はワークフローに載せない**——マージ・PR クローズを指示されたサブエージェントは
  安全クラシファイアに確率的に遮断される（理由と実績は [design-notes.md](design-notes.md)）。
- **最終結果の確認と成果物への責任**。
- **ユーザーとのコミュニケーション**。
- **全体像の把握**。

実装・レビュー・修正は、dynamic workflow が起動するサブエージェントに委譲する。
**ワークフローの範囲は 1 ステップ = 1 起動で、「レビュー承認まで」**。ワークフローは
承認済みタスクブランチの一覧を返し、監督者が統合してから次のステップのワークフローを起動する。
修正しきれないタスクはタスク単位でエスカレーションする。

**重要な制約: サブエージェントはサブエージェントを起動できない**（`agent()` の入れ子は
1 ステップまで）。「エスカレーション」の中の修正・レビューのループは、スクリプト
側の制御フロー（`if`・ループ）に開き、`agent()` には実務だけを載せる（理由と骨組みは
[design-notes.md](design-notes.md) / [workflow-script.md](workflow-script.md)）。

## 用語

- **ステップ**: 直列に並ぶ作業のまとまり。1 ステップは複数の並列タスクからなり、
  **1 つの dynamic workflow** として起動する。前のステップの承認済みブランチを監督者が topic へ
  統合してから、次のステップのワークフローを起動する。
- **タスク**: 1 ステップの中で並列に走る作業の単位。1 エージェントセッションで完結し、合否が
  一意に判定できる大きさに割る。各タスクにリスク階層 `tier`（light / standard）を付ける（§4）。
  各タスクは `計画 → 実装 → レビュー ↔ 修正ループ → polish` を回す。standard タスクのレビューは
  通常レビューと敵対的レビュー（変更はすべて誤りという前提で粗探しする独立レビュー）を並列で
  走らせ、両方が承認したときだけ承認とみなす。light タスクは通常レビュー 1 本のみ（コスト削減）。
  承認時に should-fix が残っていれば **polish（1 回だけの清掃修正）** を回す（素通り防止。
  [review-prompt.md](review-prompt.md)）。**タスクは topic へマージしない。承認済みブランチとして
  返し、統合は監督者が行う**。3 回・無進捗で直せない must-fix はタスク単位でエスカレーションする。
- **エスカレーション**: タスク内の修正ループが直しきれず未承認で返ったとき、そのタスク単体で
  行う立て直し。まず再計画エージェント（コードは書かず方針を立て直す）を 1 体呼び、その方針を
  封入してスクリプトが fix→review（別 `agent()`）を回す。直れば承認済みとして返し、直せなければ
  そのタスクを失敗として返す（1 件でも失敗があればステップは失敗として返る）。
- **統合レーン**: ワークフロー完了後に**監督者本体が**承認済みブランチを 1 本ずつ topic へ
  `git merge --no-ff` + push で取り込む単一レーン（手順は [integration.md](integration.md)）。
  `gh pr merge` は使わない（監督者セッションでもクラシファイアに遮断される）。

## 役割ごとのモデルと effort（コストを規律する）

サブエージェント（`agent()`）には**必ず `model` を明示する**（セッション既定の継承に頼らない）。
判断や実装の質が結果を左右する作業は上位モデル・既定 effort を使い、機械的な作業は下位モデル・低
effort に落として時間とトークンを節約する。厳格さは各タスクのリスク階層（§4「タスクのリスク階層」）で
変える。ユーザー指定があればそれに従う。

| 作業 | model | effort | 備考 |
| --- | --- | --- | --- |
| 実装・修正（standard タスク） | `opus` | 既定 | 判断が質を左右する |
| 実装・修正（light タスク） | `sonnet` | `medium` | docs・機械的・影響小 |
| 通常レビュー (standard タスク) | `opus` | `medium` | 差分の妥当性判断 |
| 通常レビュー (light タスク) | `sonnet` | `medium` | 差分の妥当性判断 |
| 敵対的レビュー（standard のみ） | `opus` | `medium` | light タスクでは走らせない |
| 再計画（エスカレーション） | `fable` | 既定 | 計画立案 |
| Explore 調査 | `opus` | 既定 | 監督者の意思決定材料 |
| 残件回収の単発 fix（統合後） | `sonnet` | `medium` | 小差分の清掃（[integration.md](integration.md)） |

監督者本体（このスキルを動かすセッション）は `"fable"` で動かす。別モデルで起動していたら、
ワークフローを組む前に `/model` での切り替えをユーザーに提案する。effort は `agent()` の `effort`
オプションで指定する（省略時はセッション既定を継承。理由は [design-notes.md](design-notes.md)）。

**light と standard の使い分け**（§4 で各タスクに付ける）:

- **light**: docs 追随・生成物の機械的更新・影響範囲が小さい変更（中核ロジックに触れない、数ファイル
  程度）。レビューは通常レビュー 1 本のみで敵対的レビューを省き、実装は `sonnet`。
- **standard**（既定）: ロジック・中核・挙動に関わる変更。通常＋敵対的の 2 本立て、実装は `opus`。
  **迷ったら standard にする**（誤って light にすると敵対的レビューの網が外れる）。

**fix ループの再レビューは修正の種類で軽重を変える**（[review-prompt.md](review-prompt.md)）:

- doc・コメントのみの修正（fix が `changeKind: "docs"` を返す）→ 通常レビュー 1 本・`effort: "low"`。
- ロジック修正 → タスク階層どおりのフルレビュー（standard なら通常＋敵対的）。

**フォールバック**: 指定したモデルが使えない場合は 1 つ下のレベルに落とす
（`"fable"` → `"opus"` → `"sonnet"`）。`"sonnet"` も使えなければ `model` を指定せずセッション既定を継承する。

監督者自身の意思決定のための調査は Explore エージェント（読み取り専用）に任せ、実装エージェントの
調査は肩代わりしない（各エージェントが自分で調べる。[implementation-prompt.md](implementation-prompt.md)
の §4.5）。

## 下位エージェントの起動時の注意点（監督者が守る）

dynamic workflow のスクリプトで `agent()` を呼ぶときの規律。**各エージェントが読むべき
契約**（DoD・検証観点・禁止事項・報告形式）は個別の md にあり、プロンプトへ封入する。

- **入れ子にしない**: `agent()` の中から `agent()` は呼べない（入れ子は 1 レベルまで）。
  ループ・分岐はスクリプト側の制御フローに書き、`agent()` には実務だけを載せる。
- **モデル**: 上記「役割ごとのモデル」に従い、すべての `agent()` に `model` を明示する。
- **worktree はブランチを checkout する全エージェントに付ける**: 実装・修正だけでなく、
  **レビュー・再計画にも** `isolation: "worktree"` を付ける。worktree なしのエージェントに
  checkout を指示すると、メイン作業ツリーのブランチを切り替えて並列エージェントの検証を
  汚染し、ブランチを掴んだまま終了する実害があった（[design-notes.md](design-notes.md)）。
- **detached HEAD 規律**: worktree はデフォルトブランチから分岐するため、各エージェントの
  冒頭で `git fetch origin` → `git checkout --detach origin/<起点ブランチ>` させ、push は
  `git push origin HEAD:refs/heads/<対象ブランチ>` で行わせる。ブランチ名を checkout しない
  ので「already used by worktree」衝突とブランチ先端の巻き戻しが構造的に起きない。プロンプトに
  リポジトリの絶対パスは書かず「カレントディレクトリ（割り当てられた worktree）で作業する」と
  書く（[implementation-prompt.md](implementation-prompt.md) §1）。
- **fix と review は別 `agent()`**: 修正の自己承認を防ぐため、修正と再レビューは必ず別の
  セッションにする。
- **バックグラウンド実行**: ワークフローはバックグラウンドで走るので `run_in_background`
  は指定しない。
- **構造化出力**: レビュー・再計画の結果は `schema` で構造化して返させる（後続の制御フローが
  機械的に扱えるように。スキーマは [workflow-script.md](workflow-script.md)。findings の
  `severity` は **required** にする——欠落した指摘が polish をすり抜けた実績がある）。
- **起動前に権限を解消する**: サブエージェントはファイル編集だけを自動承認する。検証
  コマンド・git・`gh`・外形動作の起動コマンド・許可リスト外の MCP は、許可リストに無いと
  実行中に権限プロンプトを出して**ワークフローを一時停止させる**。実装・レビュー・修正・
  再計画が使うコマンドを、起動前に許可リストへ追加する。プロジェクト固有の
  検証・起動コマンド（テスト・lint・ビルド・アプリ起動）はこのスキルの `allowed-tools` に
  書けないので、起動前に監督者が許可リストへ入れる。
- **`agent()` の失敗と no-op は 1 回だけリトライする**: `agent()` は throw すると `null` を
  返す。また、実作業ゼロで定型文だけ返して正常終了することがある。null・実行痕跡の無い応答は
  同じプロンプトで 1 回だけ再起動する（[workflow-script.md](workflow-script.md) の `agentRetry`）。
- **長時間ジョブの完了待ちをさせない**: 待機中に打ち切られると `agent()` が null になり成果が
  返らない。長時間ジョブ（長時間 fuzz 等）は監督者かスクリプト側で先に流すかタスクを分割し、
  少なくとも「待ちに入る前に必ず commit・push する」を契約に入れる
  （[implementation-prompt.md](implementation-prompt.md) §6.5）。
- **`args` は実オブジェクトで渡す**: JSON 文字列で渡すとスクリプト側で全フィールド undefined に
  なる。スクリプト冒頭に防御パース＋必須フィールド検査を書く（[workflow-script.md](workflow-script.md)）。
- **決定性**: `Date.now()` / `Math.random()` / `new Date()` は使えない（resume を壊す）。
  タイムスタンプ・乱数が要るときは `args` で渡すか index でプロンプトを変える。

## 監督者本体に残す（ワークフローに載せない）作業

- **統合**: 承認済みブランチの topic への取り込み・タスク PR の状態確認とクローズ
  （「6. 統合レーン」/ [integration.md](integration.md)）。マージ・PR クローズを指示された
  サブエージェントは安全クラシファイアに遮断されるため、ワークフローには載せない。
- **ワークフロー完了通知の実地検証と後始末**（[integration.md](integration.md) §1・§2）。
- **topic → デフォルトブランチの最終 PR の作成**。全ステップの統合を終えた topic を受け取り、
  監督者が最終チェックを流して PR を作る。**その最終マージはユーザーが行う**（外向きで
  後戻りしにくいため、人間のゲートを残す）。
- **失敗で返ったステップのエスカレーション**。直せないタスク・確認が必要なタスクで止まった
  ステップは、監督者が事実をユーザーに提示して次の手を決める。

## 全体フロー（監督者の仕事を段取り順に）

各手順の詳細は以下の節に、各エージェントが読む契約はリンク先の md にある。スクリプトを
書く直前・`agent()` プロンプトを組み立てる直前に、対応する md を Read する
（コンパクションで本文が失われても再取得できる）。

1. **プロジェクト前提の解決** → 「1. プロジェクト前提の解決」
2. **調査と規模判断** → 「2. 調査と規模判断」
3. **ゴールと不明点の確定** → 「3. 確認方針（既定は自律進行）」
4. **ステップとタスクの設計** → 「4. ステップとタスクの設計」
5. **権限の事前解消**（上記「下位エージェントの起動時の注意点」）
6. **topic ブランチ作成 + push** → 「5. ブランチ構成」
7. **ステップごとに繰り返す**:
   1. そのステップの dynamic workflow を起動する（承認まで。[workflow-script.md](workflow-script.md)）
   2. 完了通知を実地検証し、後始末する（[integration.md](integration.md) §1・§2）
   3. 統合レーンで承認済みブランチを topic へ取り込む（[integration.md](integration.md) §3）
   4. 残存 should-fix を回収する（[integration.md](integration.md) §4）
8. **最終結果の確認と最終 PR** → 「7. 統合結果の受け取りと完了」

各ステップの中で走る処理と、それぞれが読む契約:

- 実装エージェント（計画 + 実装）: [implementation-prompt.md](implementation-prompt.md)
- レビュー・修正・polish ステージ: [review-prompt.md](review-prompt.md)
- エスカレーション管理（再計画）: [escalation-prompt.md](escalation-prompt.md)
- 統合レーン（監督者本体の手順）: [integration.md](integration.md)
- スクリプトの骨組み: [workflow-script.md](workflow-script.md)
- 設計を選んだ理由: [design-notes.md](design-notes.md)

## 1. プロジェクト前提の解決

最初に以下を特定し、以後すべてのエージェントプロンプトに封入する
（サブエージェントは会話の文脈を持たない）。

- **検証コマンド一式**: CI 定義（.github/workflows 等）・CLAUDE.md・docs から、
  「マージ可能」と言える全チェック（テスト・lint・フォーマット・ビルド等）を特定する。
- **外形動作の確認手順**: アプリ・CLI を実際に起動して挙動を確かめる手順（`/run` や
  `/verify` スキル、起動コマンド）。レビューと監督者の統合検証が実装報告を鵜呑みにせず
  自分で駆動するために使う。
- **不可侵パス**: プロジェクト規約で触ってはならないパス・専用フローが必要なパス。
- **ブランチ・コミット規約**: デフォルトブランチ名、ブランチ命名、コミット署名
  （Co-Authored-By 等）、PR テンプレート。

## 2. 調査と規模判断

- コードベースの現状調査は **Explore エージェント**に委譲する（"very thorough"）。
  規模の実測（`wc -l` 等）程度は自分で行ってよい。
- Explore の結果は**監督者の意思決定**（ステップ分割・並列可否・規模判断・ユーザーへの
  方針提示）に使う。**実装プロンプトへは入口（関連ディレクトリ・主要クラス名を
  数個）だけを転記し、変更ファイルの列挙や行番号つきの内部構造は転記しない**。
  詳細は実装エージェントに再調査させる（理由は
  [implementation-prompt.md](implementation-prompt.md) の §0）。

## 3. 確認方針（既定は自律進行）

**既定でユーザーに逐次確認せず完了まで自律進行する。** ワークフローの起動・統合・
最終 PR の作成は確認を挟まず進める。次の「方針を決め直す判断」のときだけ止まって
確認する（自律的に下した判断は PR 本文に記録する。「8. 自律判断の PR への記録」）。

- **作業範囲の解釈が割れる**（対象・ゴール・DoD が一意に定まらない）
- **規模が当初想定から大きく増減する**（進め方の前提が変わる）
- **後戻りしにくい設計トレードオフ、仕様・設計文書の解釈の分かれ**
- **ユーザーの明示指示が既存の DoD や設計文書と矛盾する**（「9. 運用上の注意」）

**ワークフロー実行中はユーザーに確認できない**（権限プロンプト以外で実行を止められない。
理由は [design-notes.md](design-notes.md)）。そのため上記の確認は**ワークフローを起動する
前に**解消する。前提が割れたまま起動しない。途中で確認が必要になった場合は、その判断を
ワークフロー内で下さず、該当するタスクを `blocked` で返させて監督者が受け取り、ユーザーに
確認する。ステップは 1 ワークフローずつ起動するので、確認後にタスクを組み直して
そのステップを起動し直せばよい。

## 4. ステップとタスクの設計

- **ステップ分割**: 依存関係でステップを切る。前のステップの成果（topic にマージ済み）を前提にする作業は
  次のステップに置く。独立に進められる作業は同じステップの並列タスクにする。ステップが 1 つで足りるなら
  1 ステップでよい。**ステップは完全に直列**（前のステップの統合が topic を前進させるまで次は始まらない）
  なので、**依存が無いのにステップを増やすと、ただ直列化して遅くなる**。真の依存があるときだけ切り、
  独立作業はステップを増やさず 1 ステップの並列タスクに寄せる。
- **同一中核の書き換えを並列に載せない**: 同じ中核モジュールを構造的に書き換えるタスクを並列にすると、
  統合時のコンフリクトが手に負えなくなる（並列書き換えで全損した実績がある）。構造書き換えは直列
  （別ステップ）にする。
- **検分・docs 記録タスクは並列兄弟の成果に盲目**: 達成状況の検分・一覧表の記録は、対象タスクと同じ
  ステップで並列にすると兄弟タスクの成果を見られない。後続ステップに置くか、監督者が統合後に
  突き合わせて訂正する。
- **1 タスクの粒度**: 各タスクは 1 エージェントセッションで完結し、合否が一意に判定
  できる大きさに割る（達成状態を DoD として書ける単位）。1 タスクが複数ファイルに大きく
  広がると実装エージェントの精度が落ちるため、広いタスクは機能単位で分割する。
- **タスクのリスク階層を付ける**（`tier: "light" | "standard"`）。厳格さとモデル・effort を
  この階層で変える（「役割ごとのモデルと effort」）。迷ったら standard にする。
- **各タスクに構造化した仕様を書く**（実装エージェントの計画精度を上げる。曖昧な指示は推測を
  招き手戻りになる）。1 タスクにつき次を埋める:
  - **DoD**: 達成すべき状態で書く（「このファイルのこの行をこう変える」という手順にしない。§0 の
    契約と解法の分離）。
  - **受け入れ基準・検証**: 合否を判定する具体的な観点とコマンド（どのテスト・外形動作が通れば
    完了か）。
  - **スコープ境界**: やること / やらないこと、触ってよい領域 / 触ってはならない領域。
  - **調査の入口**: 関連ディレクトリ・主要クラス名を数個（変更ファイルの列挙はしない。§0）。
  - **隣接タスクとの契約**: 同じステップの並列タスクと共有する I/F・前提の一行要約。
  - **リスク階層**: 上記 `tier`。
- **DoD が曖昧なら実装させず監督者へ返させる**。実装エージェントは着手前の計画で DoD の解釈が
  一意に定まらないと判断したら、推測で実装せず `blocked` と疑問点を返す（[implementation-prompt.md](implementation-prompt.md)
  §3）。監督者がユーザーに確認する（§3 の確認方針と同じ扱い）。
- **ステップ内の並列可否はファイル競合で判断する**。worktree 分離でファイル編集自体は衝突
  しないが、別々の worktree で同じ箇所を変えると統合時の論理的競合は残る（それを解くのは
  監督者の統合レーン）。同一ファイルを触る 2 タスクを同じステップで並列にするなら「触ってよい領域 /
  触ってはならない領域」を明示する。競合が深いならステップを分けて直列にする。
- 各実装タスクは、いきなり着手させず、まず **Plan ツール**で実装計画（対象ファイル・
  変更方針・テスト方針・リスク）を立てさせる（[implementation-prompt.md](implementation-prompt.md)）。
- リファクタリングと新規テスト作成が両方あるなら、**テスト基盤 → テスト網 →
  大規模リファクタ**の順にステップを組む（回帰検出網を張ってから中核を再編する方が手戻りが
  小さい）。
- docs の一括追随も独立タスクとして同じ規律（実装 → レビュー → 修正）で行う。
  docs だけだからと素通しにしない。

## 5. ブランチ構成

- **統括**: `topic/<作業名>` をデフォルトブランチから作成して**即 push** する（タスク PR
  の base に必要）。
- **実装**: タスクごとに `topic/<作業名>--task-<連番>`（プロジェクトの命名規約があれば従う）。
  ブランチはリモートにのみ作る（worktree 内では detached HEAD で作業し
  `git push origin HEAD:refs/heads/<ブランチ名>` で push。[implementation-prompt.md](implementation-prompt.md) §1）。
  PR の base は topic ブランチ。
- **ステップの統合**: ワークフロー完了後に監督者が統合レーンで 1 本ずつ topic へ取り込む
  （[integration.md](integration.md)）。統合用の中間ブランチは作らず、タスクブランチを直接
  topic へ取り込む。
- **ステップの連鎖**: 各ステップの統合が topic を前進させるので、次のステップのタスクは更新済みの
  topic を起点にする（worktree はデフォルトブランチから分岐するため、起点に `origin/topic/<作業名>`
  を detached checkout させる）。
- **最終 PR**: 全ステップの統合後に topic → デフォルトブランチの PR を作成する。**そのマージは
  ユーザーが行う**。

## 6. 統合レーン（監督者本体が行う）

手順の詳細は [integration.md](integration.md)。統合に入る直前に必ず Read する。要点:

1. **完了通知を実地検証する**（通知・レポートは捏造されうる。journal・transcript の mtime・
   git/gh の実物で確認してから動く）。
2. **後始末**: 自分の run の `wf_<runId>-*` worktree だけを除去し、main ポインタと
   メインツリーの HEAD を確認する。
3. **統合**: 承認済みブランチを 1 本ずつ `git merge --no-ff` で topic へ取り込み、検証して push
   する。`gh pr merge` は使わない。コンフリクト解消後は**まずビルド**で構文破壊を検出する。
4. **PR の状態確認**: push 後 15〜30 秒待って MERGED 判定を確認する。OPEN のままなら
   `git merge-base --is-ancestor` で実体を検証し、stale tip なら経緯コメント付きでクローズする。
5. **残存 should-fix の回収**: findings 全件（severity 欠落含む）を topic の実コードで未解決と
   確認してから、1 本の残件ブランチにまとめて単発 fix エージェントで回収する。

## 7. 統合結果の受け取りと完了

1. ワークフローが返す構造化レポート（各タスクの `{ task, branch, pr, approved, findings,
   decisions, deferrals }`）を受け取り、実地検証のうえ統合レーンを回す（§6）。
2. **失敗・blocked で返ったタスク**は、事実（落ちた検証・直しきれなかった指摘・確認したい点）を
   ユーザーに提示してエスカレーションする。承認済みタスクは統合してよい（部分統合の帰結は
   [design-notes.md](design-notes.md)）。確認後、残りのタスクを組み直してそのステップを起動し直す。
3. **全ステップ統合済みなら**、`git fetch && git pull` でローカル topic を最新化し、topic 上で
   最終の全チェックを流す。通ったら topic → デフォルトブランチの PR を作成する。PR 本文には
   構成 PR の一覧・検証結果・意図的なトレードオフ（運用変化など）・作業全体に関わる自律判断を
   明記する。とくにレポートの `decisions`（目標変更）・`deferrals`（先延ばし）を集約し、「8.
   自律判断・目標変更・先延ばしの記録」の専用セクションに書く。**マージはしない**（ユーザーが行う）。
4. 最終報告では、何がマージされたか・レビューで何が検出されたか・失敗で残ったタスク・
   **自分の判断で変えた最終目標・先延ばしにした作業**・残課題をユーザー向けにまとめる。

## 8. 自律判断・目標変更・先延ばしの記録

自律的に下した判断（「3. 確認方針」の項目を確認せず進めたもの）は、判断内容と判断材料
（根拠・代替案）を PR 本文に記録する。とくに次の 2 つは**必ず**記録する（後から追えないと、
勝手に目標が変わった・やるはずの作業が消えたことに気づけない）。

- **最終目標・DoD・スコープを自分の判断で変えた**（当初の目標を縮小・拡大・置き換えた）。
- **当初やる予定だった作業を先延ばし、または対象外にした**（次の PR に回す、今回はやらない）。

記録先:

- **個別タスクの判断・そのタスク内の先延ばし** → 該当 タスク PR の本文。
- **作業全体の目標変更・先延ばし** → topic → デフォルトブランチの PR 本文に、次の専用セクションを
  設ける。各項目に「何を・なぜ・判断材料（根拠と退けた代替案）・残課題（先延ばしなら次にやること）」を書く。
  - `## 自律判断の記録`
    - `### 変更した最終目標・DoD・スコープ`
    - `### 先延ばし・対象外にした作業`
- **監督者がコンフリクト解消でコードを書いた場合**もここに記録する（統合レーンで監督者が
  コードに触れる唯一の場面。[integration.md](integration.md) §3）。

**バックグラウンド実行分を取りこぼさない**: ワークフロー中に実装・修正エージェントが
下した目標変更・先延ばしは、構造化レポートの `decisions`（目標変更）・`deferrals`（先延ばし）
フィールドで監督者まで上げる（[workflow-script.md](workflow-script.md)）。監督者はワークフロー完了後に
これらを集約し、上記の PR セクションと最終報告に反映する。実装エージェントに委ねた判断も、同じ記録を
タスク PR に書かせる（[implementation-prompt.md](implementation-prompt.md)）。

## 9. 運用上の注意

- ユーザーの明示指示（削除・仕様変更）が既存の DoD や設計文書と矛盾する場合は、黙って
  従わず**事実と帰結を先に提示**する（例: 削除対象が別の成果物を兼ねている、検査が opt-in
  に格下げになる）。これは「3. 確認方針」で止まる矛盾のケースにあたる。事実と代替案を
  示したうえで、判断が明らかなら妥当な解釈で進めてよい。
- ワークフローはバックグラウンドで走り、完了時に監督者へ通知が届く。通知を受けたら
  「実地検証 → 後始末 → 統合レーン → 残件回収 → 次ステップ起動（または最終 PR）」を
  滞りなく進める。
- サブエージェントの `blocked` 上申・失敗報告も鵜呑みにしない。実物（git show・テスト実行）で
  検証してから裁定する（誤認 blocked を実測で反証して再投入した実績がある）。
- 進捗とユーザーへの報告は「どのステップ・どの PR がどの状態か」を軸に簡潔に行う。
