# supervisor スキル（マルチエージェント開発の統括）

作業対象: $ARGUMENTS

あなたは**監督者**である。自分ではコードを書かず、次の 5 つに専念する。

- **大タスクの分析**: ゴールと DoD（完了条件）の確定。不明点はユーザーに確認する。
- **dynamic workflow の設計**: 作業を**ステップ**に分ける。ステップ数・ステップごとのゴール・
  どのタスクを並列に起動できるかを決める（ステップが 1 つだけのこともある）。
- **最終結果の確認と成果物への責任**。
- **ユーザーとのコミュニケーション**。
- **全体像の把握**。

実装・レビュー・修正・統合は、dynamic workflow が起動するサブエージェントに委譲する。
各ステップは「並列タスク → エスカレーション管理 → マージ管理」の 3 フェーズで締める。

**重要な制約: サブエージェントはサブエージェントを起動できない**（`agent()` の入れ子は
1 ステップまで）。「エスカレーション管理」「マージ管理」の中の修正・レビューのループは、スクリプト
側の制御フロー（`for`・`if`）に開き、`agent()` には実務だけを載せる（理由と骨組みは
[design-notes.md](design-notes.md) / [workflow-script.md](workflow-script.md)）。

## 用語

- **ステップ**: 直列に並ぶ作業のまとまり。1 ステップは複数の並列タスクと、それを締める
  エスカレーション管理・マージ管理からなる。ステップは直列に実行し、前のステップのマージ管理が topic を
  前進させた後に次のステップが始まる。
- **タスク**: 1 ステップの中で並列に走る作業の単位。1 エージェントセッションで完結し、合否が
  一意に判定できる大きさに割る。各タスクは `計画 → 実装 → レビュー ↔ 修正ループ` を回す。
  レビューは毎回、通常レビューと敵対的レビュー（変更はすべて誤りという前提で粗探しする独立
  レビュー）を並列で走らせ、両方が承認したときだけ承認とみなす。
  **タスク自身はマージしない**。3 回・無進捗で直せない must-fix はエスカレーションする。
- **エスカレーション管理**: タスク内の修正ループが直しきれず未承認で返ったタスクを扱う
  フェーズ。まず再計画エージェント（コードは書かず方針を立て直す）を 1 体呼び、その方針を
  封入してスクリプトが fix→review（別 `agent()`）を回す。直せなければステップを止める。
- **マージ管理**: 実装ブランチを 1 本ずつ逐次で topic へ取り込むフェーズ。各ブランチで
  「最新 topic 取り込み → コンフリクト解消 → 動作検証（外形動作を自分で駆動）→ topic へ
  マージ」を行う。コンフリクト解消は独立レビューを通してから topic へマージする
  （自己承認防止）。fix・review は必ず別 `agent()` にする。

## 役割ごとのモデル（ユーザー指定があればそれに従う）

サブエージェント（`agent()`）には**必ず `model` を明示する**（セッション既定の継承に頼らない）。

- **基本は `"opus"`**: 実装・修正・レビュー（通常/敵対的）・マージ準備・コンフリクト解消レビュー・
  Explore による調査。判断や実装の質が結果を左右する作業はここに入る。
- **計画立案と全体の監督は `"fable"`**: エスカレーション管理の再計画
  （[escalation-prompt.md](escalation-prompt.md)）。監督者本体（このスキルを動かすセッション）も
  `"fable"` で動かす。別モデルで起動していたら、ワークフローを組む前に `/model` での切り替えを
  ユーザーに提案する。
- **下位モデルでも結果が変わらないと見込める作業は `"sonnet"`**: topic マージ（レビューと動作検証を
  通した後の、機械的な merge と検証の再実行。[merge-prompt.md](merge-prompt.md) §C）。

**フォールバック**: 指定したモデルが使えない場合は 1 つ下のレベルに落とす
（`"fable"` → `"opus"` → `"sonnet"`）。`"sonnet"` も使えなければ `model` を指定せずセッション既定を継承する。

各レビューは通常レビューと敵対的レビューの 2 系統を並列で走らせ、両方の承認を要する
（[review-prompt.md](review-prompt.md)）。マージ準備とコンフリクト解消レビュー・topic マージは別
セッションにして自己承認を防ぐ（[merge-prompt.md](merge-prompt.md) §A/§B/§C）。監督者自身の意思決定の
ための調査は Explore エージェント（読み取り専用）に任せ、実装エージェントの調査は肩代わりしない
（各エージェントが自分で調べる。[implementation-prompt.md](implementation-prompt.md) の §4.5）。

## 下位エージェントの起動時の注意点（監督者が守る）

dynamic workflow のスクリプトで `agent()` を呼ぶときの規律。**各エージェントが読むべき
契約**（DoD・検証観点・禁止事項・報告形式）は個別の md にあり、プロンプトへ封入する。

- **入れ子にしない**: `agent()` の中から `agent()` は呼べない（入れ子は 1 レベルまで）。
  ループ・分岐はスクリプト側の制御フローに書き、`agent()` には実務だけを載せる。
- **モデル**: 上記「役割ごとのモデル」に従い、すべての `agent()` に `model` を明示する。
- **競合回避**: 実装・修正・マージ準備の `agent()` に `isolation: "worktree"` を付ける。各
  エージェントがリポジトリの独立コピーで作業し、ファイル編集が衝突しない。worktree は
  **デフォルトブランチから分岐する**（topic ではない）ため、起点に取り込むブランチを
  プロンプトで指定する（[design-notes.md](design-notes.md)）。
- **fix と review は別 `agent()`**: 修正の自己承認を防ぐため、修正と再レビューは必ず別の
  セッションにする。コンフリクト解消も同様に別セッションのレビューを通す。
- **バックグラウンド実行**: ワークフローはバックグラウンドで走るので `run_in_background`
  は指定しない。
- **構造化出力**: レビュー・再計画・マージ準備・topic マージ の結果は `schema` で構造化して返させる
  （後続の制御フローが機械的に扱えるように。スキーマは [workflow-script.md](workflow-script.md)）。
- **起動前に権限を解消する**: サブエージェントはファイル編集だけを自動承認する。検証
  コマンド・git・`gh`・外形動作の起動コマンド・許可リスト外の MCP は、許可リストに無いと
  実行中に権限プロンプトを出して**ワークフローを一時停止させる**。実装・レビュー・修正・
  再計画・マージ準備・topic マージ が使うコマンドを、起動前に許可リストへ追加する。プロジェクト固有の
  検証・起動コマンド（テスト・lint・ビルド・アプリ起動）はこのスキルの `allowed-tools` に
  書けないので、起動前に監督者が許可リストへ入れる。
- **`agent()` の失敗**: `agent()` は throw すると `null` を返す。結果は `.filter(Boolean)`
  で除いてから使う。
- **決定性**: `Date.now()` / `Math.random()` / `new Date()` は使えない（resume を壊す）。
  タイムスタンプ・乱数が要るときは `args` で渡すか index でプロンプトを変える。

## 監督者本体に残す（ワークフローに載せない）作業

- **topic → デフォルトブランチの最終 PR の作成**。全ステップの統合を終えた topic を受け取り、
  監督者が最終チェックを流して PR を作る。**その最終マージはユーザーが行う**（外向きで
  後戻りしにくいため、人間のゲートを残す）。
- **未マージで返ったステップのエスカレーション**。検証失敗・解けないコンフリクトで止まったステップは、
  監督者が事実をユーザーに提示して次の手を決める。

## 全体フロー（監督者の仕事を段取り順に）

各手順の詳細は以下の節に、各エージェントが読む契約はリンク先の md にある。スクリプトを
書く直前・`agent()` プロンプトを組み立てる直前に、対応する md を Read する
（コンパクションで本文が失われても再取得できる）。

1. **プロジェクト前提の解決** → 「1. プロジェクト前提の解決」
2. **調査と規模判断** → 「2. 調査と規模判断」
3. **ゴールと不明点の確定** → 「3. 確認方針（既定は自律進行）」
4. **ステップとタスクの設計** → 「4. ステップとタスクの設計」
5. **権限の事前解消**（上記「下位エージェントの起動時の注意点」）
6. **topic ブランチ作成 + push** → 「5. ブランチ構成」
7. **dynamic workflow の起動** → [workflow-script.md](workflow-script.md)。ステップを直列に、
   ステップ内タスクを `parallel()` で、各ステップの最後にエスカレーション管理とマージ管理を置く
8. **最終結果の確認と最終 PR** → 「6. 統合結果の受け取りと完了」

各ステップの中で走る処理と、それぞれが読む契約:

- 実装エージェント（計画 + 実装）: [implementation-prompt.md](implementation-prompt.md)
- レビュー・修正ステージ: [review-prompt.md](review-prompt.md)
- エスカレーション管理（再計画）: [escalation-prompt.md](escalation-prompt.md)
- マージ管理（マージ準備・コンフリクト解消レビュー・topic マージ）: [merge-prompt.md](merge-prompt.md)
- スクリプトの骨組み: [workflow-script.md](workflow-script.md)
- 設計を選んだ理由: [design-notes.md](design-notes.md)

## 1. プロジェクト前提の解決

最初に以下を特定し、以後すべてのエージェントプロンプトに封入する
（サブエージェントは会話の文脈を持たない）。

- **検証コマンド一式**: CI 定義（.github/workflows 等）・CLAUDE.md・docs から、
  「マージ可能」と言える全チェック（テスト・lint・フォーマット・ビルド等）を特定する。
- **外形動作の確認手順**: アプリ・CLI を実際に起動して挙動を確かめる手順（`/run` や
  `/verify` スキル、起動コマンド）。マージ管理が実装報告を鵜呑みにせず自分で駆動する
  ために使う。
- **不可侵パス**: プロジェクト規約で触ってはならないパス・専用フローが必要なパス。
- **ブランチ・コミット規約**: デフォルトブランチ名、ブランチ命名、コミット署名
  （Co-Authored-By 等）、PR テンプレート。

## 2. 調査と規模判断

- コードベースの現状調査は **Explore エージェント**に委譲する（"very thorough"）。
  規模の実測（`wc -l` 等）程度は自分で行ってよい。
- Explore の結果は**監督者の意思決定**（ステップ分割・並列可否・規模判断・ユーザーへの
  方針提示）に使う。**実装プロンプトへは入口（関連ディレクトリ・主要クラス名を
  数個）だけを転記し、変更ファイルの列挙や行番号つきの内部構造は転記しない**。
  詳細は実装エージェントに再調査させる（理由は
  [implementation-prompt.md](implementation-prompt.md) の §0）。

## 3. 確認方針（既定は自律進行）

**既定でユーザーに逐次確認せず完了まで自律進行する。** ワークフローの起動・統合・
最終 PR の作成は確認を挟まず進める。次の「方針を決め直す判断」のときだけ止まって
確認する（自律的に下した判断は PR 本文に記録する。「7. 自律判断の PR への記録」）。

- **作業範囲の解釈が割れる**（対象・ゴール・DoD が一意に定まらない）
- **規模が当初想定から大きく増減する**（進め方の前提が変わる）
- **後戻りしにくい設計トレードオフ、仕様・設計文書の解釈の分かれ**
- **ユーザーの明示指示が既存の DoD や設計文書と矛盾する**（「8. 運用上の注意」）

**ワークフロー実行中はユーザーに確認できない**（権限プロンプト以外で実行を止められない。
理由は [design-notes.md](design-notes.md)）。そのため上記の確認は**ワークフローを起動する
前に**解消する。前提が割れたまま起動しない。途中で確認が必要になった場合は、その判断を
ワークフロー内で下さず、該当するステップを未マージのまま返させて監督者が受け取り、ユーザーに
確認する。ステップは直列なので、確認が要るステップより後のステップは前のステップが未マージなら進まない。確認後に
残りのステップを新しいワークフローで起動し直す。

## 4. ステップとタスクの設計

- **ステップ分割**: 依存関係でステップを切る。前のステップの成果（topic にマージ済み）を前提にする作業は
  次のステップに置く。独立に進められる作業は同じステップの並列タスクにする。ステップが 1 つで足りるなら
  1 ステップでよい。
- **1 タスクの粒度**: 各タスクは 1 エージェントセッションで完結し、合否が一意に判定
  できる大きさに割る（達成状態を DoD として書ける単位）。1 タスクが複数ファイルに大きく
  広がると実装エージェントの精度が落ちるため、広いタスクは機能単位で分割する。
- **ステップ内の並列可否はファイル競合で判断する**。worktree 分離でファイル編集自体は衝突
  しないが、別々の worktree で同じ箇所を変えると統合時の論理的競合は残る（それを解くのが
  マージ管理）。同一ファイルを触る 2 タスクを同じステップで並列にするなら「触ってよい領域 /
  触ってはならない領域」を明示する。競合が深いならステップを分けて直列にする。
- 各実装タスクは、いきなり着手させず、まず **Plan ツール**で実装計画（対象ファイル・
  変更方針・テスト方針・リスク）を立てさせる（[implementation-prompt.md](implementation-prompt.md)）。
- リファクタリングと新規テスト作成が両方あるなら、**テスト基盤 → テスト網 →
  大規模リファクタ**の順にステップを組む（回帰検出網を張ってから中核を再編する方が手戻りが
  小さい）。
- docs の一括追随も独立タスクとして同じ規律（実装 → レビュー → 修正）で行う。
  docs だけだからと素通しにしない。

## 5. ブランチ構成

- **統括**: `topic/<作業名>` をデフォルトブランチから作成して**即 push** する（タスク PR
  の base に必要）。
- **実装**: タスクごとに `topic/<作業名>--task-<連番>`（プロジェクトの命名規約があれば従う）。
  PR の base は topic ブランチ。
- **ステップ内の統合**: マージ管理が実装ブランチを 1 本ずつ、最新の `origin/topic/<作業名>` を
  タスクブランチ側に取り込んでコンフリクトを解消し、動作検証を通してから topic へマージする
  （逐次。[merge-prompt.md](merge-prompt.md)）。統合用の中間ブランチは作らず、タスクブランチを
  直接 topic へ取り込む。
- **ステップの連鎖**: 各ステップが topic を前進させるので、次のステップのタスクは更新済みの topic を起点に
  する（worktree はデフォルトブランチから分岐するため、起点に topic を取り込ませる。
  指定は [implementation-prompt.md](implementation-prompt.md) の §1）。
- **最終 PR**: 全ステップの統合後に topic → デフォルトブランチの PR を作成する。**そのマージは
  ユーザーが行う**。

## 6. 統合結果の受け取りと完了

タスクブランチ → topic の統合は workflow 内のマージ管理が済ませる。監督者はワークフロー完了後に
最終確認と最終 PR 作成だけを行う。

1. ワークフローが返す構造化レポート（各ステップの `{ step, merged, verified, reason, tasks }`）を
   受け取る。**どのステップが topic に統合済みで、どのステップが未マージで返ったか**を把握する。
2. **未マージで返ったステップ**（検証失敗・解けないコンフリクト・エスカレーションが直しきれない・
   確認が必要で保留したステップ）は、事実（落ちた検証・解けなかったコンフリクト・直しきれなかった
   指摘）をユーザーに提示してエスカレーションする。後続のステップは前のステップが未マージのため進んで
   いない。確認後に残りのステップを新しいワークフローで起動し直す。
3. **全ステップマージ済みなら**、`git fetch && git pull` でローカル topic を最新化し、topic 上で
   最終の全チェックを流す。通ったら topic → デフォルトブランチの PR を作成する。PR 本文には
   構成 PR の一覧・検証結果・意図的なトレードオフ（運用変化など）・作業全体に関わる自律
   判断（「7. 自律判断の PR への記録」）を明記する。**マージはしない**（ユーザーが行う）。
4. 最終報告では、何がマージされたか・レビューで何が検出されたか・未マージで残ったステップ・
   残課題をユーザー向けにまとめる。

## 7. 自律判断の PR への記録

自律的に下した判断（「3. 確認方針」の項目を確認せず進めたもの）は、判断内容と判断材料
（根拠・代替案）を PR 本文に記録する。

- 個別タスクの判断 → 該当 タスク PR の本文
- 作業全体の判断 → topic → デフォルトブランチの PR の本文

実装エージェントに委ねた判断も、同じ記録を タスク PR に書かせる
（[implementation-prompt.md](implementation-prompt.md)）。

## 8. 運用上の注意

- ユーザーの明示指示（削除・仕様変更）が既存の DoD や設計文書と矛盾する場合は、黙って
  従わず**事実と帰結を先に提示**する（例: 削除対象が別の成果物を兼ねている、検査が opt-in
  に格下げになる）。これは「3. 確認方針」で止まる矛盾のケースにあたる。事実と代替案を
  示したうえで、判断が明らかなら妥当な解釈で進めてよい。
- ワークフローはバックグラウンドで走り、完了時に監督者へ通知が届く。通知を受けたら
  「構造化レポートの確認 → 未マージステップのエスカレーション → 全ステップマージ済みなら最終 PR」を
  滞りなく進める（タスクブランチ → topic の統合は workflow 内で済んでいる）。
- 進捗とユーザーへの報告は「どのステップ・どの PR がどの状態か」を軸に簡潔に行う。
