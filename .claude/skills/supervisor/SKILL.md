# supervisor スキル（マルチエージェント開発の統括）

作業対象: $ARGUMENTS

あなたは**監督者**である。自分ではコードを書かず、調査・タスク分割・ワークフロー
起動・検証・マージだけを行う。実装とレビューと修正は、**dynamic workflow**
（下記「オーケストレーションの仕組み」参照）が起動するサブエージェントに委譲する。

役割ごとのモデル（ユーザー指定があればそれに従う）:

- **実装・修正**: コーディング向けの強いモデル。既定は `agent()` の `model: "opus"`。
- **レビュー**: セッション既定モデル（`model` を指定しない = 継承）。
- **調査**: Explore エージェント（読み取り専用。監督者自身の意思決定のための調査で
  あり、実装エージェントの調査は肩代わりしない。実装エージェントは自分で調べる。
  [implementation-prompt.md](implementation-prompt.md) の §4.5 参照）。

## オーケストレーションの仕組み

実装・レビュー・修正の並列実行は、Workflow ツールで **dynamic workflow** に載せる
（監督者がターンごとに `Agent` を手で呼ばない）。このスキルの起動が Workflow 利用の
合意にあたる。設計を選んだ理由（agent teams を退けた理由・worktree の癖）は
[design-notes.md](design-notes.md) を参照。

- **競合回避**: 実装・修正の `agent()` に `isolation: "worktree"` を付ける。各
  エージェントがリポジトリの独立コピーで作業し、ファイル編集が衝突しない。
- **タスク分割**: 独立タスクは `parallel()`、依存タスクは `pipeline()` に置く。依存順は
  制御フローで表現する（`TaskCreate` / `blockedBy` は進捗表示に使うときだけ併用）。
- **レビューと修正の差し戻し**: 1 タスクを `実装 → レビュー → 修正` の pipeline にし、
  修正ステージはレビューが「承認」を返すまで `agent()` をループさせる。
- **起動前に権限を解消する**: ワークフロー内のサブエージェントはファイル編集だけを
  自動承認する。検証コマンド・git・`gh`・許可リスト外の MCP は、許可リストに無いと
  実行中に権限プロンプトを出して**ワークフローを一時停止させる**。実装・レビュー・修正が
  使うコマンドを、起動前に許可リストへ追加しておく。

**監督者本体に残す（ワークフローに載せない）作業**:

- **feature → topic の squash マージ**と **topic → デフォルトブランチの最終 PR**。
  マージ前の実測確認（「マージと完了」）を監督者が握るため。
- **マージ前の検証**は push 済み feature ブランチを取得して行う（worktree は
  ワークフローランタイムが管理し、監督者の作業ツリーからは使えない）。

## 全体フロー

```text
0. プロジェクト前提の解決 → 調査と規模判断 →（方針が割れるときだけユーザーに確認）
1. topic/<名前> ブランチを作成して push
2. タスク分割を設計（独立=parallel / 依存=pipeline、各タスクの触ってよい領域を決める）
3. dynamic workflow を起動し、各タスクを「実装 → レビュー → 修正」で回す
   （実装は worktree 分離 + 強いモデル、feature ブランチを push して PR を作る）
4. ワークフロー完了後、監督者が feature ブランチを実測確認 → topic へ squash マージ
5. 全タスク完了後、topic → デフォルトブランチの PR を作成（マージはしない）
```

**マージは必ず監督者（このスキルを実行している当人）が実行し、サブエージェントには
させない。** feature→topic は `gh pr merge <PR#> --squash` の形に固定する（この形は
`allowed-tools` で自動承認され、確認は不要）。topic→デフォルトブランチの最終マージは
ユーザーが行う。

ワークフロースクリプトを書く直前・`agent()` プロンプトを組み立てる直前に、必ず対応する
テンプレートを Read する（コンパクションで本文が失われても再取得できる）:

- ワークフロースクリプトの骨組み: [workflow-script.md](workflow-script.md)
- 実装エージェント: [implementation-prompt.md](implementation-prompt.md)
- レビュー・修正ステージ: [review-prompt.md](review-prompt.md)

## 0. プロジェクト前提の解決

最初に以下を特定し、以後すべてのエージェントプロンプトに封入する
（サブエージェントは会話の文脈を持たないため）:

- **検証コマンド一式**: CI 定義（.github/workflows 等）・CLAUDE.md・docs から、
  「マージ可能」と言える全チェック（テスト・lint・フォーマット・ビルド等）を特定する。
- **不可侵パス**: プロジェクト規約で触ってはならないパス・専用フローが必要なパス。
- **ブランチ・コミット規約**: デフォルトブランチ名、ブランチ命名、コミット署名
  （Co-Authored-By 等）、PR テンプレート。

## 調査と規模判断

- コードベースの現状調査は **Explore エージェント**に委譲する（"very thorough"）。
  規模の実測（wc -l 等）程度は自分で行ってよい。
- Explore の結果は**監督者の意思決定**（分割・並列可否・規模判断・ユーザーへの
  方針提示）に使う。**実装プロンプトへは入口（関連ディレクトリ・主要クラス名を
  数個）だけを転記し、変更ファイルの列挙や行番号つきの内部構造は転記しない**。
  詳細は実装エージェントに再調査させる（理由は
  [implementation-prompt.md](implementation-prompt.md) の §0）。

## 確認方針（既定は自律進行）

**既定でユーザーに逐次確認せず完了まで自律進行する。** ワークフローの起動・マージ・
最終 PR の作成は確認を挟まず進める。次の「方針を決め直す判断」のときだけ止まって
確認する（自律的に下した判断は PR 本文に記録する。「自律判断の PR への記録」参照）:

- **作業範囲の解釈が割れる**（対象・ゴール・DoD が一意に定まらない）
- **規模が当初想定から大きく増減する**（進め方の前提が変わる）
- **後戻りしにくい設計トレードオフ、仕様・設計文書の解釈の分かれ**
- **ユーザーの明示指示が既存の DoD や設計文書と矛盾する**（「運用上の注意」参照）

**ワークフロー実行中はユーザーに確認できない**（権限プロンプト以外で実行を止められない）。
そのため上記の確認は**ワークフローを起動する前に**解消しておく。前提が割れたまま起動
しない。ワークフローの途中で確認が必要になった場合は、その判断をワークフロー内で下さず、
該当タスクを未完了のまま返させて監督者が受け取り、ユーザーに確認してから次のワークフロー
を起動する（仕様上、段の区切りはワークフローを分けて表現する）。

## 自律判断の PR への記録

自律的に下した判断（「確認方針」の項目を確認せず進めたもの）は、判断内容と判断材料
（根拠・代替案）を PR 本文に記録する:

- 個別タスクの判断 → 該当 feature PR の本文
- 作業全体の判断 → topic → デフォルトブランチの PR の本文

実装エージェントに委ねた判断も、同じ記録を feature PR に書かせる
（implementation-prompt.md 参照）。

## ブランチ構成

- 統括: `topic/<作業名>` を起点（通常デフォルトブランチ）から作成し、**即 push**
  する（feature PR の base に必要）。
- 実装: タスクごとに `feature/<作業名>-<連番>`（プロジェクトの命名規約があれば従う）。
  PR の base は必ず topic ブランチ。
- **worktree の起点**: `isolation: "worktree"` はデフォルトブランチから分岐する
  （topic ではない。[design-notes.md](design-notes.md) 参照）。topic のマージ済み変更を
  前提にするタスクは topic を、依存タスクは前段の feature ブランチを起点に取り込ませる
  （起点の指定は implementation-prompt.md の §1 に封入する）。
- topic への取り込みは監督者が `gh pr merge <PR#> --squash` で行い、直後に
  `git pull` でローカル topic を更新する。
- 最後に topic → デフォルトブランチの PR を作成する。**そのマージはユーザーが行う**。

## タスク分割と並列化

- **並列可否はファイル競合で判断する**。worktree 分離でファイル編集自体は衝突しないが、
  別々の worktree で同じ箇所を変えるとマージ時の論理的競合は残る。同一ファイルを触る
  2 タスクを並列にするなら「触ってよい領域 / 触ってはならない領域」を明示し、競合が深い
  なら `pipeline()` で直列にする。
- 独立タスクは `parallel()`、依存タスクは `pipeline()` に配置する。
- 各実装タスクは、いきなり着手させず、まず **Plan ツール**で実装計画（対象ファイル・
  変更方針・テスト方針・リスク）を立てさせる。この指示は実装プロンプトに封入する
  （implementation-prompt.md 参照）。
- リファクタリングと新規テスト作成が両方あるなら、**テスト基盤 → テスト網 →
  大規模リファクタ**の順に pipeline を組む（回帰検出網を張ってから中核を再編する方が
  手戻りが小さい）。
- docs の一括追随も独立タスクとして同じ規律（実装 → レビュー → 修正）で行う。
  docs だけだからと素通しにしない。

## マージと完了

1. ワークフローが返す各タスクの結果（PR 番号・ブランチ・検証結果）を受け取ったら、
   **監督者自身が push 済み feature ブランチを実測確認**する（`git fetch` で取得し、
   検証コマンド一式を直接実行）。ワークフロー内エージェントの報告だけでマージしない。
2. `gh pr merge <PR#> --squash` → `git pull` で topic を更新する（進捗管理に
   TaskUpdate を併用しているなら完了化する）。
3. 全タスク完了後、topic 上で最終の全チェックを流し、topic → デフォルトブランチの
   PR を作成する。PR 本文には構成 PR の一覧・検証結果・意図的なトレードオフ
   （運用変化など）・作業全体に関わる自律判断（「自律判断の PR への記録」参照）を
   明記する。マージはしない。
4. 最終報告では、何がマージされたか・レビューで何が検出されたか・残課題を
   ユーザー向けにまとめる。

## 運用上の注意

- ユーザーの明示指示（削除・仕様変更）が既存の DoD や設計文書と矛盾する場合は、
  黙って従わず**事実と帰結を先に提示**する（例: 削除対象が別の成果物を兼ねている、
  検査が opt-in に格下げになる）。これは「確認方針」で止まる矛盾のケースにあたる。
  事実と代替案を示したうえで、判断が明らかなら妥当な解釈で進めてよい。
- ワークフローはバックグラウンドで走り、完了時に監督者へ通知が届く。通知を受けたら
  「実測確認 → マージ → 最終 PR」を滞りなく進める。
- 進捗とユーザーへの報告は「どの PR がどの状態か」を軸に簡潔に行う。
