# エスカレーション（再計画エージェント）のプロンプト構成（テンプレート）

タスク内の修正ループ（3 回・無進捗で打ち切り）が must-fix を直しきれずに未承認で返ったタスクを、
**そのタスク単体で**扱う段階。**subagent は subagent を起動できない**ため、エスカレーションは
スクリプト側の制御フローに開く（[workflow-script.md](workflow-script.md) の `runTask`
の中の未承認分岐）。このプロンプトは、未承認になったタスクごとにそのタスクのパイプラインの中で
1 体呼ぶ**再計画エージェント**のもの。

- **再計画エージェント**（このファイル）: 未承認タスクの残り指摘を分析し、直し方の方針を
  立て直す。**コードは書かない**（計画だけ返す）。
- その後の fix・review は、スクリプトの `fixReviewLoop` が**別々の `agent()`**として起動する
  （fix は [implementation-prompt.md](implementation-prompt.md)、review は
  [review-prompt.md](review-prompt.md) の修正・レビュー契約に従う）。fix と review を別
  セッションにするのは修正の自己承認を防ぐため。

## なぜ「再計画」から入るか

タスク内の修正ループが 3 回・無進捗で直せなかった指摘を、同じやり方でもう一度回しても
同じ壁に当たる。先に「なぜ直せなかったか」を分析して方針を立て直してから fix に入る。
この方針を fix プロンプトに封入することで、後続の fix ループが前と同じ失敗を繰り返さない。

## プロンプトに含める契約

`agent(prompt, { model: 'fable', isolation: 'worktree', ... })` で起動する（計画立案にあたるので
`'fable'`。タスクブランチの checkout・読み取りを行うので worktree を付け、detached checkout の
規律に従わせる（[review-prompt.md](review-prompt.md) のレビューステージと同じ手順）。
`'fable'` が使えなければ `'opus'` に落とす。レビュアー・修正者とは別セッション。

### 対象の特定

- ステップ番号、topic ブランチ名。
- 未承認で返ったタスクの `{ タスク DoD, タスクブランチ名, PR 番号, 残った must-fix 指摘の
  一覧（severity・file・line・summary・rationale） }`（`replanPrompt(esc)` の `esc` に対応）。
- 検証コマンド一式（方針が検証を通せるものか判断するため）。

### 実行内容

- そのタスクの残った must-fix 指摘を読み、**なぜ修正ループで直せなかったか**を
  分析する（例: 指摘同士が矛盾している、DoD の解釈が実装とずれている、根本原因が別ファイル
  にある、テストの期待値が誤っている）。
- 必要ならタスクブランチ・関連コードを Read して原因を特定する（detached checkout。
  読み取りのみ）。
- そのタスクの**直し方の方針**を立てる: どこを・どういう順で直すか、何を検証で確かめるか。
  解決不能と判断したら「解決不能」と理由を明示する（監督者へのエスカレーション材料になる）。

### 禁止事項

- **コードを書かない・ファイルを編集しない**（修正は後続の fix `agent()` が担当）。
- レビューの approve をしない。
- メイン作業ツリー・他のディレクトリのチェックアウトに触れない。

### 報告形式（`schema` で構造化。workflow-script.md の `PLAN` に対応）

- `plan`（文字列）: そのタスクの再修正方針。「どこを・どう直すか」「何を検証するか」「解決
  不能ならその理由」を含める。この方針が後続の fix プロンプトに封入される。

## スクリプト側の扱い（workflow-script.md 参照）

- 再計画のあと、そのタスクのパイプラインが `fixReviewLoop`（fix→review を別 `agent()` で
  最大 3 回・無進捗打ち切り）を回す。fix プロンプトには再計画の `plan` を封入する。
- 直れば、そのタスクは承認済みブランチとして返り、監督者の統合レーンが topic へ取り込む
  （[integration.md](integration.md)）。
- それでも承認が出なければ、そのタスクを失敗として返す。監督者が事実をユーザーに提示して
  エスカレーションし、対応後にタスクを組み直してそのステップを起動し直す（先に承認・統合済みの
  タスクは topic に残る）。
