# 実装・修正エージェントの契約（あなた自身が読む）

スクリプトが 3 つの場面で起動する。どれも `isolation: 'worktree'` を付け、`schema` は
[scripts/task-workflow.js](scripts/task-workflow.js) の `IMPL` を使う。

| 場面 | label | model | 役割タグ | 起点 |
| --- | --- | --- | --- | --- |
| 初回の実装 | `impl:<タスク>` | standard はリードを継承 / light `sonnet` | `impl:a` | `origin/<起点ブランチ>`（`resumeFrom` があればタスクブランチ） |
| 修正ラウンド | `fix:<タスク>#<ラウンド>` | 同上 | `impl:a` | `origin/<タスクブランチ>` |
| 実装の差し替え | `impl-b:<タスク>` | リードを継承 | `impl:b` | `origin/<タスクブランチ>` |

**読む節は場面ごとに違う。** プロンプトに「読むのは §… である」と書かれているので、
`grep -n '^## '` で節の開始行を取り、その範囲だけを Read する。**全文を開かない**——この契約は
14KB あり、当たらない節まで読むと調査と実装に使える余地が毎ターン削れる（§0）。

## 0. 契約を渡し、解法は渡さない（スキルを直す人向け。エージェントは読まなくてよい）

渡した `prompt` はエージェントの会話履歴の一部になる。会話ループは毎ターン履歴全体を送り直すので、
**プロンプトは実行中ずっと毎ターン送り直され、トークンを使い続ける**。ツール呼び出しが 100 回に
及ぶ実装では、その固定費が 100 回分積み上がり、調査と実装に使える余地を毎ターン削る。

そこで、**毎ターン参照する価値がある「契約」だけを渡し、一度読めば足りる「解法」は渡さない**。

- **渡す（契約）**: DoD、検証コマンド一式、不可侵パス、ブランチとコミットの規約、
  隣接タスクとの契約の一行要約、調査の入口（関連ディレクトリと主要な名前を数個）
- **渡さない（解法）**: 変更するファイルの一覧、行番号つきの手順、リードが Explore で得た
  内部構造の詳細

解法まで書くと 3 つ困る。(1) プロンプトが太り毎ターンの送り直しで無駄が出る、(2) 実装モデルの
推論を殺してタイピストにする（強いモデルを指定した意味が消える）、(3) リードの調査ミスを
そのまま引き継ぐ。

## 1. 作業場所と push

共通の前置き（[scripts/task-workflow.js](scripts/task-workflow.js) の `preamble`）で、割り当てられた worktree の中で
`git checkout --detach <起点>` まで済んでいる。

```text
カレントディレクトリ（割り当てられた worktree）で作業する。他のディレクトリのチェックアウトに
触れない。リポジトリの絶対パスはプロンプトに書かれていない。

- commit はプロジェクトの署名規約に従う（brief.md に書いてある）。
- push は `git push origin HEAD:refs/heads/<タスクブランチ>` で行う
  （ブランチ名を checkout しない。リモートにだけ作る）。
- **意味のある単位ができたら、その都度 commit して push する。** 検証が全部通ってから
  まとめて push しない。あなたが途中で落ちても、push 済みのものだけは次に引き継げる。
- **マージしない・stacked PR に触らない。** タスクブランチを stacked PR へ積むのはリードで（`gh stack`）、
  マージするのはユーザーである。`gh stack` も `gh pr merge` も呼ばない。
```

## 2. 何を作るか

リードが台帳から転記する。

- **DoD**: 達成すべき状態で書く。「このファイルのこの行をこう変える」という手順にしない。
- **受け入れ基準と検証**: 合否を判定する観点と、実際に叩くコマンド。
- **先行タスクの成果**: 参照すべきファイルとブランチ名を**一行要約**で渡す（全差分を貼らない。
  詳しく見たければ `git show` で自分で見る）。
- **判断してよい範囲**: 設計判断を委ねるなら、その範囲を明示する。下した判断は根拠と
  退けた代替案とともに `decisions` に入れる。

`light` を束ねたタスクでは、束ねた全 DoD を並べ、**1 ブランチ・1 PR にまとめる**ことを書く。

## 3. 着手前に計画を立てる

**コードを 1 行も書く前に計画を立てる。** 行き当たりばったりの実装は手戻りを生み、修正ラウンドを
余計に回す。計画には次を必ず含める。

- **DoD → 変更 → テスト → リスクの対応づけ**: DoD の各項目を、どのファイル・どの変更・
  どのテストで満たすかに落とす（変更するファイルは自分の調査で特定する）。
- **前提と仮定**: 実装が頼っている前提（既存 I/F の挙動、隣接タスクの成果）を書き出す。
- **壊しうる箇所と、それを捕まえる方法**: 境界値・エラー経路・後方互換と、どの検証で捕まえるか。

計画の要点は `summary` に含める。実装が計画からずれたら、その理由も書く。

**DoD が曖昧なら実装せずに返す。** 計画の段階で DoD の解釈が一つに定まらない、または受け入れ
基準を具体化できないと判断したら、**推測で実装に入らず** `blocked: true` と `questions` を返す。
リードがユーザーに確認する。曖昧なまま作ると意図と違うものができてやり直しになる。

## 4. 調査は自分で行う

渡るのは入口（どこを見るか）だけで、該当箇所の特定と構造の把握は自分で行う。**プロンプトに
「どのファイルをどう直すか」が無いのは正しい状態であり、不足ではない**（§0）。

- **コードを読む前に引き継ぎノートを読む**（`<ベース>/notes/task<番号>/impl-*.md`）。前のラウンドの
  実装が、読んだ箇所・実行した検証と結果・構造の要点を残している。ここから始めると再探索が減る。
- 広く見て回る段階（全体構造の把握・命名規約の調査）は Explore サブエージェントに委ねて自分の
  文脈を節約してよい。ただし**編集するファイルは直接 Read する**（Explore は抜粋しか返さない）。
- プロジェクト規約は起動時に CLAUDE.md と memory を自動で読み込むので、**プロンプトに全文を
  再掲しない**。代わりに `.claude/CLAUDE.md` と `.claude/rules/`（実際のパス）を必ず読むよう
  一行で指示する。タスクに直結する最重要ルール 1〜2 個だけは、見落とし防止に要点を書いてよい。

## 5. 境界

- 不可侵パス（`brief.md` に書いてある）。
- 並列に走る他タスクとの分担（触ってよい領域 / 触ってはならない領域）。
- **テストを書くタスクでは「バグを見つけても直さず、最小の再現を報告する」**と指示する
  （直すかどうかはリードが判断する）。
- 挙動を変えないリファクタリングでは「既存テスト（golden 等）が 1 件でも割れたら挙動が変わった
  証拠。テストではなくリファクタ側を直す」と明示する。

## 6. 検証と push

`brief.md` の検証コマンド一式を列挙し、**すべて通してから push** する。外形動作の確認手順が
あるものは実際に起動して動かす。

**長時間かかるジョブの完了を待つ前に、必ず commit して push する。** 待っている間に打ち切られると
返り値が失われる。

自分が下した判断（根拠・退けた代替案）は `decisions` で返し、引き継ぎノート（§9）にも書く。
PR 本文はこれらを材料に、専用のエージェントが最後に書く（[pr-body-prompt.md](pr-body-prompt.md)）。

`resumeFrom` が渡されているときは、前コミット（`resumeFrom.sha`）までは実装済みなので、
**最初からやり直さず続きから始める**。`resumeFrom.transcriptDir` が渡されていれば、前のランの
`agent-*.jsonl` を読んで経緯を拾ってよい（ただし引き継ぎノートを先に読む。そちらの方が短い）。

## 7. 修正ラウンドでの作法

open のレビューを直す場面。**JSON を直接書かず `<スクリプト>/review.py` を引数付きで呼ぶ**
（詳細は [review-store.md](review-store.md)）。

```text
1. 対象を取る。open だけが出る（closed / rejected は見ない・直さない）。

   <スクリプト>/review.py list --dir <ベース>/notes/task<番号>

   **ここに無い指摘は直さなくてよい。** 裁定が却下した指摘（nit など）は closed / rejected に
   なっていて一覧に出ない。掘り起こさない。

2. 各件を直す。rating が must-fix のものから先に直す。

3. 各件に必ずコメントを残す。何をどう直したか、対応するコミットの SHA を書く。

   <スクリプト>/review.py comment \
     --dir <ベース>/notes/task<番号> --id r3 \
     --commenter impl:a \
     --comment "空スライスの早期 return を追加 (a1b2c3d)"

4. **直せない・直さないと判断した件にもコメントを残す。** 「指摘が誤りだと考える理由」
   「このタスクの範囲外だと考える理由」を書く。根拠は実物の場所で示す
   （「呼び出し元 mod.rs:71 の assert で非空が保証されている」）。挙げられないなら直す。

5. **status は動かさない**（review.py status は裁定だけが呼べる。スクリプトも拒む）。
   直ったかどうかを判定して閉じるのは裁定役である。

6. commit して push する。
```

**範囲を広げない。** open の指摘を直すことだけを行い、ついでの整理をしない。新しい問題を
持ち込むと修正ラウンドが 1 回増える。

## 8. 実装の差し替え（impl-b）

再計画エージェントの方針が封入される。

```text
前の実装は 3 ラウンド回しても指摘を直しきれなかった。方針から見直す。
前の実装に引きずられるな。前のコミットを捨ててよい。

封入された方針:
<再計画エージェントが返した plan>
```

`<ベース>/notes/task<番号>/replan-r0.md` を先に読む。捨てるものと踏んではいけない地雷が
書いてある。実装したら**同じタスクブランチに push する**（新しいブランチを作らない）。

**前のラウンドで open だった指摘はそのまま残っている。** 作り直した差分に対してレビューが
新しく立て直されるので、あなたは既存の open にコメントしなくてよい（裁定が差分を見て裁く）。

## 9. 引き継ぎノート

終える前に `<ベース>/notes/task<番号>/impl-r<ラウンド>.md` を書く（`mkdir -p` してから）。
前のラウンドのノートの要点で今も有効なもの（構造の要点・まだ確かめていない箇所）は
引き継いで書く——次のラウンドはラウンド番号が最大の 1 本だけを読む。

```markdown
# impl r<ラウンド>

## 読んだファイルと要点
- <パス>: <何をしているか。次のエージェントが再読しなくて済む粒度で>

## 変えたところ
- <パス>: <何をどう変えたか。なぜ>

## 実行したコマンドと結果
- <コマンド>: <結果>

## まだ確かめていない箇所
- <次に見るべき点>
```

会話をそのまま貼らない。次のエージェントがコードを読み直さずに済む要約にする。

## 10. 報告の形（`schema` で返す）

| フィールド | 中身 |
| --- | --- |
| `worktree` | あなたに割り当てられた worktree の絶対パス（`git rev-parse --show-toplevel` の出力）。役目を終えた worktree をワークフローが消すのに使う。空だと消されずに残る |
| `branch` | タスクブランチ名 |
| `commits` | この段階で積んだコミットの SHA |
| `changeKind` | `docs`（doc とコメントだけ）/ `logic`（ロジックに触れた）。再レビューの軽重に使う |
| `summary` | 変更の概要と、計画からずれたならその理由 |
| `verified` / `verification` | 検証コマンドを全部通したか。何をどう流したか |
| `blocked` / `questions` | DoD が曖昧で実装に入れないときだけ |
| `answered` | 修正ラウンドのとき。コメントを返した review の件数 |
| `decisions` | 自分の判断でタスクの目標・DoD・スコープを変えたもの（根拠と退けた代替案） |
| `deferrals` | やる予定だった作業を先送り・対象外にしたもの（次に何をすべきか） |

`decisions` と `deferrals` は、**同じ内容を引き継ぎノートにも書く**。PR 本文エージェントが
これを読んで PR に載せる。

## 11. 禁止事項

- **PR を作らない・本文を書き換えない。** `gh pr create` / `gh pr edit` / `gh pr review` を
  使わない。タスク PR は全レビューが決着してからリードが作る（[integration.md](integration.md) §2）。
- **マージしない・stacked PR に触らない。** stacked PR へ積むのはリードで
  （[integration.md](integration.md)）、マージするのはユーザーである。`gh pr merge` も `gh stack` も使わない。
- **status を動かさない**（`review.py status` は裁定だけが呼べる。スクリプトが拒む）。
- メイン作業ツリー・他のディレクトリのチェックアウトに触れない。新しい worktree を作らない。
- 他のタスクのブランチに触れない。
