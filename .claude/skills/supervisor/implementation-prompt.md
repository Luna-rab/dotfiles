# 実装エージェント（計画 + 実装）のプロンプト構成（テンプレート）

起動方法: dynamic workflow のスクリプト内で `agent(prompt, opts)` として起動する。
`opts` は実装用モデルを明示（standard は `model: "opus"`）、`isolation: "worktree"`
（リポジトリの独立コピーで作業させ、ファイル編集の競合を防ぐ）を付ける。ワークフローが
バックグラウンド実行なので `run_in_background` の指定は不要。1 タスクは
`計画 → 実装 → レビュー ↔ 修正ループ → polish` を回し、このプロンプトが計画 + 実装のステージに
あたる（レビュー・修正ステージは [review-prompt.md](review-prompt.md) 参照）。
**タスクはマージしない**——承認済みブランチの topic への統合は、ワークフロー完了後に
監督者本体が行う（[integration.md](integration.md)）。

## 0. プロンプトの原則: 契約を渡し、解法は渡さない

サブエージェントに渡した `prompt` は、そのサブエージェントの会話履歴の一部に
なる。LLM の会話ループは毎ターン履歴全体を再送するので、**プロンプトは実行中
ずっと（コンパクションされるまで）毎ターン再送され、トークンを消費し続ける**。
ツール呼び出しが 100 回に及ぶ実装エージェントでは、その固定コストが 100 回分
積み上がり、調査・実装に使える有効コンテキストを毎ターン圧迫する。

そこで、**毎ターン参照される価値がある「契約」だけを渡し、一度読めば足りる
「解法」は渡さない**。

- **封入する（契約）**: DoD（何を・どこまで）、検証コマンド一式、不可侵パス、
  ブランチ・コミット規約、隣接タスクの結果の一行要約、調査の入口（関連
  ディレクトリ・主要クラス名を数個）。これらは実装中に何度も参照される。
- **封入しない（解法）**: 変更ファイルの列挙、行番号つきの手順、監督者が
  Explore で得た内部構造の詳細。これはエージェント自身に調べさせる。

解法まで書くと弊害が 3 つある。(1) プロンプトが肥大化し毎ターン再送で無駄が
出る、(2) 実装モデルの推論を殺してタイピスト化する（強いモデルを指定した意味が
消える）、(3) 監督者の調査ミスをエージェントがそのまま継承する。監督者の
Explore 調査は「分割・並列可否・規模」を監督者が判断するためのものであり、
実装プロンプトへ丸ごと転記しない（[SKILL.md](SKILL.md) の「調査と規模判断」参照）。

以下の各節は「契約として封入すべき項目」を列挙したものである。省略した契約は
サブエージェントには存在しないのと同じになる。

## 1. 起点の固定と detached HEAD 規律（必須）

`isolation: "worktree"` の worktree は**デフォルトブランチ**から分岐する（topic
ブランチや親セッションの HEAD ではない）。topic に既にマージ済みの変更を前提にする
タスクでは、そのままだと起点に必要なファイルが無い。また、worktree 内でブランチ名を
checkout すると、そのブランチを worktree が掴んだままになり（「already used by worktree」
衝突）、後続の処理を壊す。最初の手順として次を指示する:

```text
カレントディレクトリ（割り当てられた worktree）で作業する。他のディレクトリの
チェックアウトに触れない。
1. `git fetch origin` を実行する。
2. `git checkout --detach origin/topic/<作業名>` で起点に detached で載る
   （ブランチは作らない）。
3. 起点に存在するはずのファイル（前のステップまでにマージ済みの成果物）を確認してから
   作業を開始する。
4. push は `git push origin HEAD:refs/heads/topic/<作業名>--task-<連番>` で行う
   （リモートにだけブランチを作る）。
```

起点のブランチ／コミット SHA と「存在するはずのファイル」は監督者が具体的に書く。
**プロンプトにリポジトリの絶対パスを書かない**（書くと worktree ではなくメインツリーを
操作する事故が起きる）。ステップは直列に流れ、各ステップの統合が topic を前進させる。
そのため次のステップのタスクは更新済みの topic を起点にする。同じステップの並列タスク同士は
互いの成果を起点にできない（まだ topic に入っていない）ので、ステップ内で依存が生じる作業は
ステップを分ける。

## 2. 背景と要件

- 何を・なぜ・どこまで（DoD）。**どう直すか（解法）は書かない**（§0）。
  DoD は「達成すべき状態」で書き、「このファイルのこの行をこう変える」という
  手順に落とさない。
- 先行タスクの成果物は、参照すべきファイル・PR 番号と**一行要約**で渡す
  （全差分を貼らない。詳細が要ればエージェントが `git show` 等で自分で見る）。
- 設計判断を委ねる場合は「判断してよい範囲」を明示し、下した判断は判断材料
  （根拠・代替案）とともに PR 本文に記録させる。

## 3. 実装前の計画立案（精度を上げる要）

実装前に **Plan ツール**で計画を立てさせる。行き当たりばったりの実装は手戻りを生み、修正
ループ（トークン）を余計に消費する。計画には次を必ず含めさせる。

- **DoD → 変更 → テスト → リスクの対応づけ**: DoD の各項目を、どのファイル・どの変更・どの
  テストで満たすかに落とす（変更ファイルは自分の調査で特定する。監督者は列挙しない。§0）。
- **前提と仮定の明示**: 実装が依存する前提（既存 I/F の挙動、隣接タスクの成果）を書き出す。
- **想定リスクと確認方法**: 壊しうる箇所（境界値・エラー経路・後方互換）と、それを検証で
  どう捕まえるか。

計画の要点は PR 本文に含めさせ、実装が計画から乖離したらその理由も書かせる。

**DoD が曖昧なら実装せず返す（推測で進めない）**: 計画段階で DoD の解釈が一意に定まらない、
または受け入れ基準が具体化できないと判断したら、**推測で実装に入らず** `blocked: true` と
確認したい点（`questions`）を返す。監督者がユーザーに確認してからタスクを組み直す
（[SKILL.md](SKILL.md) §3・§4）。曖昧なまま実装すると、監督者の意図と違うものを作って
やり直しになり、かえって高くつく。

## 4. 境界の明示

- プロジェクトの不可侵パス（SKILL.md の「プロジェクト前提の解決」で特定したもの）。
- 並列エージェントとの分担（触ってよい領域 / 触ってはならない領域）。
- 本体コード変更の可否。**テスト作成タスクでは「バグを発見しても修正せず、
  最小再現を報告する」**と指示する（修正の要否は監督者が判断する）。

## 4.5 調査は自分で行う（通常起動のエージェントと同じ）

このエージェントは通常起動の general-purpose エージェントと同じく、自分で調べて
実装する。監督者から渡るのは入口（どこを見るか）だけで、該当箇所の特定・構造
把握は自分で行う。プロンプトに「どのファイルをどう直すか」が無いのは正しい状態で
あり、不足ではない（§0）。

- 広く見て回る段階（全体構造の把握・命名規約の調査など）は Explore サブ
  エージェントに委ね、自分の文脈を節約してよい。ただし**編集するファイルは
  直接 Read する**（Explore は抜粋しか返さず、編集には不十分）。
- プロジェクト規約（コーディングルール・参照渡し禁止などの禁止事項）は、
  general-purpose エージェントが起動時に CLAUDE.md と memory を自動で読み込むため、
  **プロンプトに全文を再掲しない**。代わりに `.claude/CLAUDE.md` と
  `.claude/rules/`（プロジェクトの実際のパス）を**必ず読むよう一行で指示する**。
  タスクに直結する最重要ルール 1〜2 個だけは、見落とし防止に要点を書いてよい。

## 5. 挙動不変の定義（リファクタリングの場合）

「既存テスト（golden 等）が 1 件でも割れたら挙動が変わった証拠。テストではなく
リファクタ側を直す」と明示する。

## 6. 検証

プロジェクトの検証コマンド一式を列挙し、**すべて green にしてから push** させる。

## 6.5 長時間ジョブの前に必ず commit・push する

長時間ジョブ（長時間 fuzz・ベンチマーク等）の完了待ちの間にエージェントが打ち切られると、
返り値が null になり成果の所在が失われる（成果自体は worktree に残る）。長時間ジョブを含む
タスクには「**ジョブの待ちに入る前に、それまでの作業を必ず commit して push する**」を契約に
入れる。可能なら、ジョブは監督者が先に流すか、タスクを「起動 + 中間成果の commit/push」と
「結果記入」に分ける（[SKILL.md](SKILL.md)「下位エージェントの起動時の注意点」）。

## 7. 完了時の作法

- コミットはプロジェクトの署名規約に従う（例: 末尾に
  `Co-Authored-By: Claude <モデル名> <noreply@anthropic.com>` を付ける。モデル名は
  そのエージェントが実際に動いているモデルを書く）。
- §1 の規律で push し（`git push origin HEAD:refs/heads/topic/<作業名>--task-<連番>`）、
  `gh pr create --base topic/<作業名>` で PR を作成（本文は日本語。
  設計判断・仕分け一覧など、レビューの判断材料になる情報を含める）。
- **マージはしない**（統合はワークフロー完了後に監督者が行う）。
- 返り値（レビュー・修正ステージと監督者に渡る。[workflow-script.md](workflow-script.md) の
  `IMPL`）には次を含める:
  - **PR 番号・URL・タスクブランチ名・変更概要・検証結果・課された DoD の要約**。DoD の要約は、
    監督者が統合時に「課題が解決されたか」を確認するのに使う（[integration.md](integration.md)）。
  - **`changeKind`**（修正ステージのみ）: 変更が doc・コメントのみなら `"docs"`、ロジックを含むなら
    `"logic"`。再レビューの軽重を決めるのに使う（doc のみなら軽量な通常レビュー 1 本で再確認）。
  - **`decisions`**（配列）: 自分の判断で**タスクの目標・DoD・スコープを変えた**もの。
  - **`deferrals`**（配列）: **やる予定だった作業を先延ばし・対象外にした**もの。
  - decisions・deferrals は返り値に入れるだけでなく、**同じ内容を タスク PR 本文にも記録**する
    （判断材料として、なぜそうしたか・退けた代替案・残課題を添える。[SKILL.md](SKILL.md) §8）。
  worktree はランタイム管理で後続ステージから見えないためパスは残さない。後続のレビュー・統合は
  push 済みのタスクブランチ経由で行う。
