# 統合レーン（監督者本体の手順）

ワークフロー完了後に、承認済みタスクブランチを topic へ取り込む段階。**すべて監督者本体が
自分の作業ツリーで直接行う**。サブエージェント（ワークフロー内・単発 Agent とも）にマージや
PR クローズを指示すると安全クラシファイアに確率的に遮断されるため、統合は委譲しない
（理由と実績は [design-notes.md](design-notes.md)）。同じ理由で **`gh pr merge` は監督者
セッションでも使わない**。`git merge` + `git push` で統合すれば、GitHub は head コミットの
base 到達を検出してタスク PR を自動的に MERGED 判定にする。

以下を §1 → §5 の順に行う。

## §1. 完了通知の実地検証（レポートに基づく行動の前に必ず行う）

完了通知・構造化レポート・usage 値は真正性の証拠にならない。実行中の run に「completed」通知が
誤発火し、PR 番号・マージ・失敗談まで含む精巧な**捏造レポート**が届いた実績がある。レポートに
基づく行動（統合・エスカレーション・後始末）の前に必ず:

1. `git log origin/<topic>` / `gh pr list --base <topic> --state all` で成果の実在を確認する。
2. ワークフローの transcript ディレクトリの `journal.jsonl` に完了記録（`type=="result"` 行）が
   あるか確認する（「started」だけなら未完了）。
3. `ls --time-style=full-iso` で transcript の mtime と現在時刻を比較する。**今も成長していれば
   run は生きている**。
4. 生きている run の後始末（worktree remove・ブランチ削除）は厳禁。先に `TaskStop` で止め、
   静止を確認してから §2 に進む。

レポートの `approved` の各ブランチについても、`git fetch origin` 後に origin 上の実在と
push 済みコミットの有無を確認する（実行痕跡の無い承認は no-op 応答の疑いがある）。

## §2. 後始末（worktree とメインツリーの健全化）

ワークフローは正常完了しても `wf_*` worktree を大量に残すことがある。統合の前に:

1. `git worktree list` で残留を確認し、**自分が起動した run の `wf_<runId>-*` だけ**を
   `git -C <パス> status --porcelain` でクリーンと確認してから `git worktree remove --force` で
   除去 → `git worktree prune`。パターンを `wf_*` 全体や `.claude/worktrees/` 一括にしない
   （他プロセスの worktree を削除した事故がある）。
2. `git rev-parse main origin/main`（デフォルトブランチ名で読み替える）の一致を確認する。
   ずれていたら worktree エージェントが共有側のポインタを動かした事故なので
   `git branch -f main origin/main` 等で復旧する。
3. メインツリーの HEAD がブランチに載っているか確認する（`git rev-parse --abbrev-ref HEAD` が
   `HEAD` なら detached。`git checkout <デフォルトブランチ>` で復旧する）。

## §3. 統合（1 本ずつ・単一レーン）

承認済みブランチを 1 本ずつ、次の手順で topic へ取り込む。並列にしない（並列マージは
コンフリクトする）。

1. `git fetch origin` し、topic を checkout して最新化する（`git pull`）。
2. **冪等チェック**: `git merge-base --is-ancestor origin/<タスクブランチ> origin/<topic>` で
   既に取り込み済みなら、そのブランチはスキップする（再開・再実行時の二重マージ防止）。
3. `git merge --no-ff origin/<タスクブランチ>` で取り込む。
4. **コンフリクトが出たら**: 解消してから、**検証より先にまずビルド**を流す。機械的な解消
   （両側結合）は「共有末尾を含む hunk」で閉じ括弧を落として構文を壊すことがあり、ビルドが
   最速で検出する。併せて、コンフリクトにならない**片側だけの新規ファイル**が相手側の変更
   （新フィールド等）を欠いていないか、全体コンパイル（テストのビルドを含む）で洗い出す。
   解消の規模が大きい・判断を伴う場合は、単発の fix エージェント（`Agent` ツール、
   `isolation: "worktree"`）に解消を委譲し、別の単発レビューエージェントで解消差分を独立
   レビューしてよい（**マージ自体は委譲しない**。解消済みブランチを受け取って監督者がマージする）。
5. **検証**: コンフリクトを解消したマージの直後は検証コマンド一式＋外形動作をフルで流す。
   コンフリクトの無いマージは速い検証（ビルド等）に留めてよいが、**ステップの全ブランチを
   取り込み終えた時点で必ず検証コマンド一式＋外形動作をフルで 1 回流す**（ファイル単位で独立でも
   論理コンフリクトはあり得る。レビュー・実装の報告値を最終的な合否判定には使わない）。
6. 検証が落ちたら、原因のブランチを特定して単発 fix エージェント（worktree）＋独立レビューで
   直させ、直った ブランチを取り込み直す。直せなければそのブランチを `git reset --hard` で
   巻き戻して外し、ユーザーへのエスカレーション材料にする（先に取り込んだ分は topic に残る）。
7. `git push` で topic を前進させる。

**監督者がコンフリクト解消でコードを書いた場合**は、解消の内容と判断を最終 PR の
「自律判断の記録」に書く（SKILL.md §8。統合レーンは監督者がコードに触れる唯一の場面）。

## §4. タスク PR の状態確認と残件回収

1. **MERGED 判定の確認**: topic を push した直後はタスク PR が OPEN のままのことがある。
   15〜30 秒待って `gh pr list --base <topic> --state open` を確認する。
2. **OPEN が残っていたら**: (a) `git merge-base --is-ancestor` で実体の取り込みを検証、
   (b) 成果物の実在を実物（テスト数・生成物等）で確認、(c) 実体が入っているのに OPEN なら
   ブランチ先端が古いマージコミット等で置き換わった stale tip なので、経緯コメント付きで
   PR をクローズしブランチを削除する。実体が入っていなければ統合漏れなので §3 に戻る。
3. **残存 should-fix の回収**: レポートの findings から should-fix を拾う。このとき
   severity の有無に関わらず findings **全件**を対象にする（severity 欠落の指摘がすり抜けた
   実績がある）。各指摘を**マージ済み topic の実コードで未解決と確認**してから（polish で解決済み
   でも findings には残るため、レポートだけを根拠にフォローアップを起こさない）、未解決分を
   **1 本の残件ブランチにまとめて**単発 fix エージェント（worktree・PR 作成）→ レビュー
   （小差分なら監督者自身の diff 確認で足りる。ロジックを含むならレビューエージェント 1 体）→
   §3 の手順で統合する。件数が多くてもブランチを分けない（往復が 1 回で済む）。
   大きい残存指摘は回収せず、最終 PR の「残課題」としてユーザーへ提示する。

## §5. 次のステップへ

- 次のステップがあれば、更新済みの topic を起点にそのステップのワークフローを起動する
  （タスクの起点指定は `origin/<topic>` の detached checkout。
  [implementation-prompt.md](implementation-prompt.md) §1）。
- 全ステップの統合が済んだら最終 PR へ（SKILL.md §7）。
