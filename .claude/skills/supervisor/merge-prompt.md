# マージ管理のプロンプト構成（テンプレート）

承認済みの実装ブランチを **単一レーンのマージキュー**で topic へ取り込む段階。各タスクはレビューを
通った時点でこのキューへ投入され、キューは投入順（＝承認された順）に 1 本ずつマージを処理する。
同時に走るマージは常に 1 本になる（並列マージは topic でコンフリクトするため）。**subagent は
subagent を起動できない**ため、マージ管理はスクリプト側のマージキュー（Promise チェーン
`enqueueMerge` と、1 本分を処理する `mergeBranchToTopic`）に開く
（[workflow-script.md](workflow-script.md)）。マージ管理は次の 3 種類の `agent()` からなる。

- **マージ準備エージェント**（このファイル §A、`model: 'opus'`, worktree）: 最新 topic をタスクブランチ
  側に取り込み、コンフリクトを解消し、動作検証（検証コマンド一式 + 外形動作）を実測する。
  コンフリクトが無く検証も通れば、そのまま topic を前進させて `merged: true` で返す。
- **コンフリクト解消レビューエージェント**（このファイル §B、`model: 'opus'`）: マージ準備が
  コンフリクトを解消した（＝コードを書いた）場合に、その解消差分を独立にレビューする。
  自己承認を防ぐため別セッション。
- **topic マージエージェント**（このファイル §C、`model: 'sonnet'`, effort `'low'`）: コンフリクト解消の
  レビュー通過後・動作検証通過後に、topic を前進させる。別セッションが最終ゲートを引く。手順が機械的
  なので下位モデル・低 effort で足りる。

スクリプトは各ブランチについて「準備 →（コンフリクトがあればレビュー→必要なら fix）→
（検証が通らなければ fix）→ topic マージ」を回す。fix・review はスクリプトが別々の `agent()` として
起動する（fix は [implementation-prompt.md](implementation-prompt.md)、review は
[review-prompt.md](review-prompt.md)）。

## この段階が満たす契約

- **単一レーンで直列マージ**: topic への並列マージはコンフリクトするため、同時に走らせるマージは
  常に 1 本にする。承認された順にキューへ投入し、1 本ずつ取り込む。各回で最新 topic（前のブランチが
  入った状態）を取り込むので、進行中 topic に対する論理コンフリクトを 1 本ずつ捕まえられる。
  タスクの完了を全部待たずに、承認された成果から順に topic へ載る。
- **動作の自己確認**: 実装エージェント・レビュアーの報告（「テストは通った」「動く」）を
  鵜呑みにせず、**外形動作をマージ準備エージェントが自分で駆動**して確かめる（アプリ・CLI を起動する）。
  報告値の追試は過去に誤りがあったため必須。検証コマンド一式（テスト・lint・ビルド）は、最新 topic の
  取り込みで差分が入ったとき（統合結果が未検証のとき）に実行する。取り込みが no-op で統合ツリーが
  レビュー済みツリーと同一なら、その再実行は重複なので省き、外形動作の駆動だけ行う（§A-3）。
- **コンフリクト解消の自己承認を防ぐ**: 解消はコードを書く行為なので、独立レビューを通して
  から topic に載せる。コンフリクトの無いブランチは新規コードを書かないので、このレビューは
  飛ばす。
- **topic マージは別セッション**: topic へ最終確定するゲートを、マージ準備とは別セッションが引く。

## §A. マージ準備エージェント

`agent(prompt, { model: 'opus', isolation: 'worktree', schema: MERGE })` で起動する。worktree は
デフォルトブランチから分岐するので、冒頭で `git fetch origin` して対象タスクブランチと topic を取得
させる。

### 対象の特定

- ステップ番号、topic ブランチ名、対象タスクの `{ タスクブランチ名, PR 番号, DoD 要約 }`。
- 検証コマンド一式、外形動作の確認手順（アプリ・CLI の起動、`/run`・`/verify`、動作コマンド）。

### 実行内容（この順で行わせる）

1. **最新 topic の取り込み**: タスクブランチを checkout し、最新の `origin/topic/<作業名>` を
   マージする（`git merge origin/topic/<作業名>`）。**この取り込みで差分が入ったか、それとも既に最新で
   何も変わらなかったか（already up-to-date の no-op）を記録する**。後段の検証の要否を分けるのに使う。
2. **コンフリクト解消**: コンフリクトが出たら解消してコミットする。**解けないコンフリクトが
   あれば** `merged: false`・`hadConflict: true` と内容を `reason` に入れて返す（fix/topic マージに
   進まず、スクリプトがエスカレーションする）。コンフリクトの有無を `hadConflict` に入れる。
3. **動作検証**: マージ後のツリーが動くことを実測する。取り込み結果によって流し方を変える。
   - **取り込みが no-op（コンフリクト無し・差分ゼロ = 既に最新）だった場合**: マージ後のツリーは
     タスク内レビューが検証済みのツリーと同一なので、**検証コマンド一式（テスト・lint・フォーマット・
     ビルド）の再実行は省く**。ただしレビューが必ずしも駆動しない**外形動作だけは 1 回自分で駆動して
     確かめる**（「報告を鵜呑みにしない」原則を保つ）。これが通れば `verified: true`。
   - **取り込みで差分が入った場合（コンフリクトを解消した／topic が先に進んでいた）**: 統合結果は
     未検証なので、**検証コマンド一式をすべて実行し、外形動作も駆動する**。相互に依存しないコマンド
     （テスト・lint・フォーマット・ビルド）は**並列に流してよい**。外形動作の駆動は**そのタスクが触った
     機能に絞る**（変更と無関係な全機能の起動までは求めない。light タスクでフルアプリ起動が過剰なら要点
     だけ確かめる）。
   - **どれかが落ちたら** `merged: false`・`verified: false` と失敗内容を `reason` に入れて返す
     （スクリプトが fix ループに回す）。
4. **push**: ここまでの結果をタスクブランチに push する（コンフリクト解消コミットを後続の
   レビュー・topic マージが見られるように）。
5. **コンフリクトが無かった場合は、この場で topic へマージしてよい**: コンフリクトが無く
   （`hadConflict: false`）検証も通ったなら、マージ準備エージェント自身が topic へマージして
   `merged: true` で返してよい。この場合は §B の独立レビューと §C の topic マージエージェントを
   通さない。理由は、コンフリクトを解消していない = マージ準備エージェントは新しいコードを 1 行も
   書いておらず、既にレビュー・承認済みのタスクブランチをそのまま topic へ足すだけなので、
   別セッションによる再レビュー（自己承認の防止）が不要だから。topic へマージする手順と冪等
   チェックは §C の topic マージエージェントと同じものを行う。

### 報告形式（`schema` で構造化。workflow-script.md の `MERGE` に対応）

- `branch`（文字列）: 取り込み後のタスクブランチ名。
- `hadConflict`（真偽）: 最新 topic の取り込みでコンフリクトが出たか。
- `verified`（真偽）: 動作検証が通ったか（no-op 取り込みでテスト再実行を省いた場合は、外形動作が
  通れば true）。
- `merged`（真偽）: この場で topic へマージできたか（コンフリクトが無く §A-5 で自分でマージした
  ときだけ true。コンフリクトを解消した場合は §C の topic マージエージェントがマージするので false）。
- `reason`（文字列）: 未マージ・未検証・解けないコンフリクトの内容、または実行した検証の要約。

## §B. コンフリクト解消レビューエージェント

`agent(prompt, { model: 'opus', schema: REVIEW })`。マージ準備がコンフリクトを解消した
場合に、その解消差分をレビューする。別セッションで自己承認を防ぐ。

### 対象と観点

- 対象は「マージ準備がコンフリクト解消のために加えた差分」（topic 取り込み前のタスクブランチとの
  diff、またはマージコミットの解消内容）。`git fetch` して checkout し確認する。
- 観点: 解消が両側の意図を正しく保っているか（どちらかの変更を握り潰していないか）、解消の
  結果が DoD と矛盾しないか、テスト・アサーションを弱めていないか。**タスク本体のコードの
  再レビューはしない**（それはタスク内のレビューが済ませている。ここで見るのは解消差分だけ）。

このコンフリクト解消レビューも、他のレビューと同じく `runReview` を通すので厳格さはタスクの
`tier` に従う（standard は**通常レビューと敵対的レビューを並列で走らせ**、light は通常レビュー
1 本。[workflow-script.md](workflow-script.md)）。敵対的版
（`adversarialConflictReviewPrompt`）は「解消差分はすべて誤り」という前提で、どちらかの変更を
握り潰していないか・DoD と矛盾しないか・テストを弱めていないかを反証する立場で確かめる
（[review-prompt.md](review-prompt.md) の「敵対的レビューステージ」と同じ規律）。両方が承認した
ときだけ承認とみなす。

### 報告形式

- workflow-script.md の `REVIEW`（`approved`・`findings`）。承認が出なければスクリプトが fix
  ループに回す。

## §C. topic マージエージェント

`agent(prompt, { model: 'sonnet', effort: 'low', schema: MERGE })`。コンフリクト解消のレビュー通過後・
動作検証通過後に、topic を前進させる最終ゲート。マージ準備とは別セッション。ここでの作業は
既定の手順（冪等チェック → merge → 検証コマンドの再実行）で、コードを書かず判断も伴わないため、
下位モデル（`'sonnet'`）・低 effort（`'low'`）でも結果は変わらない。

### 実行内容（この順で行わせる）

1. **冪等チェック（最初に必ず行う）**: そのブランチが既に topic に入っていないか確認する
   （`git merge-base --is-ancestor <branch> origin/topic/<作業名>` 等）。**既に入っていれば
   以降を行わず `merged: true` で返す**（resume でこのステージが再実行されても壊れないように）。
2. **topic の前進**: `git fetch origin` して topic を最新化し、タスクブランチを topic へ
   取り込んで push する。ここで新たなコンフリクトが出たら（他ブランチが先に入った等）、
   `merged: false` と内容を `reason` に入れて返す。
3. **取り込み後の検証**: topic 上で検証コマンド一式をもう一度流し、統合による論理コンフリクトを
   実測で捕まえる。落ちたら `merged` の扱いを含め `reason` に明記して返す。

### 禁止事項

- **コードの新規実装・修正はしない**（検証が落ちたら直さず未マージで返す。修正は前のステップの fix が
  担当）。
- **topic → デフォルトブランチのマージはしない**（最終マージはユーザー）。

### 報告形式

- workflow-script.md の `MERGE`。`merged: true` なら topic を前進できた。

## 監督者側の受け取り（workflow-script.md 参照）

- ステップの全ブランチを topic へマージできたら、そのステップは `merged: true`。次のステップはこの topic を起点に進む。
- どれか 1 本でも「解けないコンフリクト・通らない検証・承認されない解消」で止まったら、
  スクリプトはステップ全体を `merged: false` で返す。**ただし先に承認・マージ済みのブランチは既に topic に
  入っている**（承認された順に非同期でマージするため）。各タスクの `merged` で何が topic に載ったかを
  追える。後続のステップは進まない。監督者が `reason` と「どのタスクまで topic に入ったか」を
  ユーザーに提示してエスカレーションし、対応後に残りのステップを新しいワークフローで起動し直す。
