# PR 本文エージェントの契約（スクリプトが封入する）

全レビューが closed か rejected になった後、ワークフローの最後に 1 回だけ走る。**PR の本文を
書いてファイルに置くだけ**で、PR は作らない（作るのはリード。[integration.md](integration.md)）。

```javascript
agent(prBodyPrompt(), {
  label: `pr-body:${task.id}`, phase: 'PR',
  model: 'opus', isolation: 'worktree', schema: PRBODY })
```

**この PR を読むのは人間である。** レビューの往復（review.json）は作業記録であって成果物では
ないので、そのまま貼らない。読者が知りたいのは「**この変更で何がどう変わるか**」である。

## 1. 対象に載る

共通の前置き（`workflow-script.md` の `preamble`）で、worktree の中で
`git checkout --detach origin/<タスクブランチ>` まで済んでいる。

```bash
git diff origin/topic/<作業名>...HEAD      # この PR に入る差分
git log origin/topic/<作業名>..HEAD --oneline
```

読むものは 4 つ。

| 読むもの | 何を取るか |
| --- | --- |
| 差分とコミット | 実際に何が変わったか。**これが一次情報である** |
| `<ベース>/notes/task<番号>/review.json`（`review.py list --all`） | 指摘の往復。とくに `rejected` で「このタスクでは直さない」とした残件 |
| `<ベース>/notes/task<番号>/impl-*.md` | 実装が何をどう変えたか、どんな判断をしたか |
| `<ベース>/brief.md` | PR テンプレートの有無、**PR タイトルを検査する job があるか** |

## 2. 書く先

`<ベース>/notes/task<番号>/pr-body.md` に本文を書く（パスはプロンプトに封入されている）。
**このファイル 1 つだけを書く。** リポジトリのファイルを編集しない。

リポジトリに PR テンプレート（`.github/PULL_REQUEST_TEMPLATE.md` など）があれば、**その見出しを
残したまま**中身を埋める。無ければ次の構成にする。

```markdown
## 概要

<この PR で何が変わるか。挙動の変化を 1〜3 行で>

## 変更による挙動の変化

- <操作 X をすると、これまでは A だったが、これからは B になる>
- <画面・コマンド・API レスポンスなどで観測できる差分を列挙>

## 確認項目

- [ ] <操作手順> を行うと <観測できる結果> になる

## 補足

<理解が難しい箇所・注意を払うべき箇所。残件があればここに書く。無ければ節ごと省く>
```

## 3. 書き方の方針

- **コードの変更点を逐一説明しない。** 差分を見れば分かる。**挙動の変化**を中心に書く。
- **コードについて触れるのは、理解が難しい箇所・注意を払うべきと判断した箇所に限る。**
- **「正しく」「正常に」「適切に」など解釈に余地のある言葉を使わない。** 何がどう変わるかを
  具体的な事象で書く。
  - 悪い: 「エラーが正常に処理されるようになった」
  - 良い: 「空入力を渡すと終了コード 1 と `empty input` を返す。これまでは panic して
    スタックトレースが出ていた」
- **確認項目は観測できる事象で書く。** コード内部の状態（変数・フラグ）は観測できないので
  書かない。
- **挙動が変わらない変更（リファクタリング・docs）では、そう書く。**「挙動の変化はない。
  確かめた方法は〜」と、何をもって変わらないと判断したかを添える。
- **残件を隠さない。** `rejected` にした指摘のうち「妥当だがこのタスクでは直さない」と裁定した
  ものは、補足に 1 行ずつ残す（何を・なぜ・次に何をすべきか）。
- **レビューの往復そのものを書かない。** 「レビューで 5 件指摘され 3 件直した」は読者の役に
  立たない。直した結果として何がどうなったかだけを書く。

## 4. タイトル

`title` として返す。リードがそのまま `gh pr create --title` に渡す。

```
[supervisor #<topicPR番号> task<番号>] <種別>: <件名>
```

- `<種別>` は `feat` / `fix` / `docs` など、そのリポジトリの既存 PR タイトルに倣う
  （`git log` と `gh pr list` で確かめる）。
- **`brief.md` に「PR タイトルを検査する job がある」と書いてあるときは接頭辞を末尾に回す**
  （`fix: パーサの境界値を直す [supervisor #100 task1]`）。先頭に置くと検査が落ちる。
- `<topicPR番号>` はプロンプトに封入されている topic PR の番号である。

## 5. 禁止事項

- **PR を作らない・push しない・コードを編集しない。** `gh pr create` / `gh pr edit` を使わない。
  書いてよいのは `pr-body.md` 1 つだけである。
- **review.json を書き換えない**（`review.py new` / `comment` / `status` を呼ばない）。読むだけ。
- **レビューをやり直さない。** 新しい問題を見つけても、この段では指摘として立てない。差分を読んで
  「本文に書くべき注意点」だと判断したら補足に書き、`notes` にもその旨を残す。
- メイン作業ツリー・他のディレクトリのチェックアウトに触れない。

## 6. 報告の形（`schema` は `PRBODY`）

| フィールド | 中身 |
| --- | --- |
| `title` | PR のタイトル（§4 の形。リードがそのまま使う） |
| `bodyFile` | 書いた本文の絶対パス |
| `behaviorChange` | `true` / `false`。挙動が変わるか（リードが topic PR の本文をまとめるときの材料） |
| `notes` | 何を根拠に挙動の変化を書いたか。確かめられなかった点があればそれも |
