# レビュー・修正ステージのプロンプト構成（テンプレート）

1 タスクは `計画 → 実装 → レビュー ↔ 修正ループ` を回す。計画・実装は
[implementation-prompt.md](implementation-prompt.md)、この文書はレビューと修正の 2 つの
ステージを扱う。**タスクは自分ではマージしない**——ステップ内の全ブランチのマージは
マージ管理がステップの最後に行う（[merge-prompt.md](merge-prompt.md)）。

**レビューと修正は 3 か所で共用する**（[workflow-script.md](workflow-script.md) の
`fixReviewLoop`）:

- **タスク内**: 実装直後のレビューと、承認まで（3 回・無進捗打ち切り）の修正ループ。
- **エスカレーション**: 打ち切ったタスクを、再計画（[escalation-prompt.md](escalation-prompt.md)）
  の方針を封入して直すループ。
- **マージ検証**: マージ管理で動作検証が落ちたブランチ・コンフリクト解消が承認されない
  ブランチを直すループ（[merge-prompt.md](merge-prompt.md)）。

いずれも **fix と review は必ず別 `agent()`**にする（修正の自己承認を防ぐ）。

**standard タスクのレビューは通常レビューと敵対的レビューの 2 系統を並列で走らせる**
（[workflow-script.md](workflow-script.md) の `runReview`）。両方が承認したときだけそのレビューを
承認とみなし、指摘は両者を結合し**重複を除いて**修正ステージへ渡す。通常レビューは「実行内容」の
観点で差分の妥当性を確かめ、敵対的レビューは「加えられた変更はすべて誤りである」という前提で
粗探しをする（「敵対的レビューステージ」）。**light タスク（docs・機械的・影響小）は通常レビュー
1 本のみ**で敵対的レビューを省く（コスト削減。タスクの `tier` で切り替える。[SKILL.md](SKILL.md)
「役割ごとのモデルと effort」）。

責務分界: **レビューは検証のみ（ファイルを編集しない）**、**修正は指摘の反映のみ
（マージしない）**。タスク内の修正ループで直しきれない must-fix は、未承認のまま
エスカレーション管理へ引き継ぐ（[escalation-prompt.md](escalation-prompt.md)）。

## レビューステージ（検証のみ）

`agent(prompt, opts)` で起動する。`opts` は `model: "opus"`（差分の良し悪しを判断する作業なので
基本モデルを使う）。ファイルを編集しないので worktree は不要。
実装ステージの worktree はランタイムが管理し、レビューステージからは直接見えないため、
push 済みのタスクブランチを対象にする（remote のタスクブランチを `git fetch` して
checkout してから読む）。ブランチ名は前のステップの実装ステージの返り値から受け取る。

プロンプトは [implementation-prompt.md](implementation-prompt.md) の §0 と同じ原則で
組む: レビュー観点（契約）は封入するが、監督者が想定する不具合の中身や直し方
（解法）は渡さず、レビュアー自身に差分を読ませて判断させる。プロジェクト規約は
CLAUDE.md/memory を自分で読ませ、全文をプロンプトに再掲しない。

プロンプトには以下の契約を**すべて**含める。

### レビューの前提（確証バイアスを断ち、外部信号に接地する）

レビュー精度を最も落とすのは「このコードは正しい・安全」という思い込みと、自分の推論だけで正しさを
担保しようとすることである。次を明示する（通常・敵対的の**両方**に封入する。根拠と出典は
[design-notes.md](design-notes.md)）。

- **コードが正しい・安全だと仮定しない。** 実装エージェントの報告・PR タイトル・PR 説明・
  コミットメッセージは「主張」であって事実ではない。安心材料を鵜呑みにせず、**差分そのものを
  根拠に判断する**（「安全」という前提の刷り込みが見逃しの最大要因という実証がある）。
- **確信は推論でなく実測で裏づける。** 「ここにバグがある」と結論する前に、可能なら実際に再現
  させる（テストを足して落ちることを見る、検証コマンドを流す）。推論だけで確信した指摘は、実測で
  裏が取れないうちは確信度を下げる（推論で存在しない欠陥を全員が承認し、1 つのテストで却下された
  事例がある）。
- **承認を自己完結させない。** レビューの正しさは、別セッションのレビュー・実行テスト・マージ管理の
  実測検証といった外部信号に接地させる（自己批判だけでは精度は上がらない）。

### 対象の特定

- タスクブランチ・PR 番号・ベースブランチ・変更内容の要約
  （`git fetch origin` して当該ブランチを checkout する手順を明示する）。変更内容の要約・PR 説明は
  **実装側の主張として扱い、事実確認は差分で行う**（上記「レビューの前提」）。

### 実行内容

- `/code-review` スキルの実行（effort high。docs のみの変更なら medium で可）。
  対象はベースブランチとの差分。
- **タスク特化の検証観点**を監督者が設計して指定する。例:
  - 挙動不変リファクタ: 移動された関数本体をベース版と機械的に突き合わせる
    （`git show` で旧版を取得し、行 diff・ハッシュ比較）。テストの本数・
    アサーションの保全。可視性（pub 等）の緩み。
  - テスト作成: カバレッジの過不足（DoD との突き合わせ）、アサーション強度
    （「実行して panic しないだけ」になっていないか）、期待値が仕様・設計文書と
    矛盾しないか。
  - **実装エージェントの報告値の追試**: カバレッジ実績・実行時間・「warning
    なし」等の主張は鵜呑みにせず再測定させる（過去に報告値の誤りが実際にあった）。
- 検証コマンド一式がタスクブランチで通ることの実測。

### 重大度の規律と根拠（誤った must-fix は修正ループを無駄に回す）

重大度は**アンカー付きの定義と具体例**で一貫させる（曖昧な定義だと LLM の割り当てがぶれる。few-shot
の具体例が較正に効くという実証がある。[design-notes.md](design-notes.md)）。

- **`must-fix`**: DoD 未達・正しさのバグ・既存の挙動を壊す変更・テストやアサーションの弱体化。
  例:「境界値 0 で配列外参照して panic する」「golden テストが 3 件割れている」。
- **`should-fix`**: 動くが直すべき問題（可読性を大きく損なう・明確な非効率・軽微な仕様逸脱）。
  例:「エラーを握り潰していてログに残らない」。
- **`nit`**: 好み・些末。例:「命名の統一」。**nit を must-fix に昇格させない**（must-fix が
  1 つでも残ると修正エージェントが起動しトークンを使う）。

- **各 must-fix は具体的な根拠を添え、可能なら実測で裏づける**: どのファイル・どの行が、どんな
  入力・状態で、どう失敗するか（再現手順・落ちる検証）を書く。実際に再現・確認した方法（テスト実行・
  検証コマンド、または「差分の精読のみ」）を `confirmedBy` に記す。**実測で裏が取れない推論だけの
  指摘は must-fix にせず** `should-fix` に落とすか「反証を試みたが確証なし」に回す。
- **無視してよいものは指摘しない**: 主たる防御が妥当なのに多重防御を求める、タスクのスコープ外の
  スタイル、といった投機的指摘は出さない（過剰指摘はレビューの信頼を下げ、修正ループを無駄に回す）。
- **重複を避ける**: 同じ箇所への同旨の指摘は 1 件にまとめる（通常＋敵対的の結合時にスクリプトが
  file:line で重複除去するが、レビュアー自身も同じ観点を繰り返さない）。

### 禁止事項

- **修正の禁止**: ファイルを編集しない（修正は次のステージが担当）。
- GitHub への approve / review 投稿はしない（自己承認になるため）。

### 報告形式（構造化して返す）

修正ステージが機械的に扱えるよう、`schema` で次を返させる（workflow-script.md の `REVIEW`）:

- `approved`（真偽）: 問題なしなら true。
- `findings`（配列）: 各要素に `severity`（must-fix / should-fix / nit）・
  `file`・`line`・`summary`・`rationale`・`confirmedBy`（どう裏づけたか。実行したテスト・検証コマンド、
  または「差分の精読のみ」）。
- 検証したが問題なしと判断した観点、却下した候補も記載させる。

## 敵対的レビューステージ（変更はすべて誤りという前提で粗探しする）

通常レビューと**並列に**、同じタスクブランチを対象にもう 1 体の `agent()` を起動する
（通常レビューと同じ `model: "opus"`。[workflow-script.md](workflow-script.md) の `runReview`）。
狙いは、通常レビューが「変更は概ね正しい」と見なすことで見落とす前提の誤りを拾うこと。

プロンプトは通常レビューの契約（レビューの前提・対象の特定・禁止事項・重大度の規律・報告形式）を
封入する。ただし**汎用の `/code-review` は通常レビューが既に回しているので繰り返さない**（二重実行は
コストだけ増える）。敵対的レビューは下の反証観点に集中し、通常レビューと違う角度から粗探しする。
加えて次を明示する。

- **加えられた変更はすべて誤りであると仮定する。** 正しさを確かめるのではなく、誤りである証拠を
  探す立場でレビューする。既定は「却下」で、動いていても仕様・DoD を満たさなければ落とす。
- **前提知識ゼロ（cold-start）で差分だけを見る。** 実装エージェントの説明・通常レビューの結論・
  PR の物語を持ち込まない（アンカリングの連鎖を断つため。[design-notes.md](design-notes.md)）。
- **構造的な盲点を優先的に精査する**（LLM レビューが実際に見逃すのはここで、コメントの嘘ではない
  という実証がある。[design-notes.md](design-notes.md)）:
  - 競合状態・TOCTOU（確認と使用のずれ、共有状態への非原子的アクセス）。
  - タイミング・side-channel（秘密値に依存する分岐・比較の非定数時間性）。
  - 認可・権限ロジックの合成（複数条件の組合せで権限が漏れる経路）。
  - 境界値・null・エラー経路・後方互換の破壊。
- **DoD の取り違え・抜け**、**テストの弱さ**（実行して panic しないだけ、常に真のアサーション、
  期待値が仕様と矛盾）、**実装エージェントの報告値**（カバレッジ・実行時間・「warning なし」）の
  誤りを追試する。
- **確信した欠陥は実測で裏づける**（可能なら再現テストを足して落ちることを見る。推論だけの確信は
  確証なしとして扱い、`confirmedBy` に明記する）。
- 反証できなかった観点は「反証を試みたが問題なし」として理由とともに記載させる
  （通常レビューと同じ `REVIEW` スキーマで返す）。

禁止事項は通常レビューと同じ（ファイルを編集しない、GitHub へ approve/review を投稿しない）。
コンフリクト解消レビューでも同様に、通常のコンフリクト解消レビューと並列で敵対的版を起動する
（`adversarialConflictReviewPrompt`。[merge-prompt.md](merge-prompt.md)）。

## 修正ステージ（レビューが承認するまでループ）

ワークフロー側で、レビューが `approved: true` を返すまで修正 `agent()` を繰り返す
（[workflow-script.md](workflow-script.md) の `fixReviewLoop`）:

```text
prevMustFix = review の must-fix 件数
while (!review.approved && round < 上限) {
  fix    = agent(修正プロンプト(branch, review.findings), { ...implOpts(task), isolation: "worktree" })
  // doc・コメントのみの修正（fix.changeKind === "docs"）は通常レビュー 1 本・effort 低で再確認、
  // ロジック修正はタスク階層どおり（standard なら通常＋敵対的）
  review = 再レビュー(fix.branch, fix.changeKind)
  if (review の must-fix 件数 >= prevMustFix) break  // 無進捗 = スタック
  prevMustFix = review の must-fix 件数
}
```

- 修正エージェントのモデルはタスク階層に従う（`implOpts`: standard は `"opus"`、light は
  `"sonnet"` + effort `"medium"`）。対象タスクブランチを起点に worktree で作業する。
- **修正が doc・コメントのみか（`changeKind`）を返させる**。再レビューの軽重を決めるのに使う
  （doc のみなら軽量な通常レビュー 1 本、ロジック修正はフルレビュー）。
- **打ち切り条件は 2 つ**: (1) 上限回数（例: 3 回）、(2) 無進捗（修正しても must-fix
  件数が減らない）。回数上限だけだと、修正が効かないタスクで上限まで無駄にエージェント
  （トークン）を消費する。
- **タスク内ループがどちらで抜けても未承認のまま返す**。残った must-fix 指摘を要約して
  返り値に入れ、エスカレーション管理へ引き継ぐ（[escalation-prompt.md](escalation-prompt.md)）。
  監督者が直接受け取るのは、ステップ全体が未マージで返ったときだけ。
- **エスカレーション・マージ検証のループでは**、封入する方針が変わる。エスカレーションでは
  再計画の `plan` を、マージ検証では「どの検証・外形動作が落ちたか」を fix プロンプトに封入する。
- 監督者による仕分けをプロンプトに封入する: must-fix / should-fix は必須、nit は
  費用対効果で指示、対応不要とした指摘には理由を付けて明示する。
- 完了条件: 修正後に検証コマンド一式を再実行して push（PR 更新）、修正内容と
  検証結果を返す。**マージはしない**。

## 再レビューの粒度

- doc・コメント修正程度 → 軽量な再確認。
- ロジック修正 → 上記ループでフルの再レビューを回す。

どちらの場合も、承認はステップのマージの前提にすぎない。マージ管理が topic 取り込み後に検証
コマンド一式を実測し、外形動作も自分で駆動して確かめる（レビュー・修正の報告値を最終的な
合否判定には使わない。[merge-prompt.md](merge-prompt.md)）。
