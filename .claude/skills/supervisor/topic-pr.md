# topic PR（計画と進行状況の置き場）

**topic PR** は、base ブランチ（デフォルトブランチまたは `release/*`）へ向けた
`topic/<作業名>` の PR である。この 1 本を作業の入口として最初に作り、**全体の計画とタスクの
進行状況を本文に持つ**。台帳（`<ベース>/ledger.md`）は git の追跡対象外で統合ツリーを外すと
消えるので（[ledger.md](ledger.md)）、**ユーザーが GitHub 上で読める記録はこの本文である。**

```
main ← topic/<作業名>（この PR）← 各タスクのマージコミット
```

**タスク PR の base でもある。** 決着したタスクはリードが PR にしてから topic へ取り込むので
（[integration.md](integration.md)）、topic には空コミット 1 つと各タスクのマージコミットが載る。
**最終マージ（topic → base）はユーザーが 1 回行う。**

計画をファイルにしてコミットしない。

## いつ何をするか

| 場面 | 操作 |
| --- | --- |
| `SKILL.md` §4（タスク設計の直後） | `gh pr create --draft` で作る（本文は「進行中の本文」） |
| 1 タスクを topic へ取り込んだ後（[integration.md](integration.md) §5） | `gh pr edit --body-file` で差し替える |
| タスクを `blocked` / `failed` で打ち切ったとき | 同上 |
| `SKILL.md` §8（仕上げ） | 「最終版の本文」に差し替え、`merged` が 1 件以上あれば `gh pr ready` |

ワークフローを起動したときは更新しない（`runId` は台帳にだけ控える）。

## 本文はファイルに書いてから渡す

**本文を `--body` の引数に直接書かない。** 本文には `` `merged` `` のようなコード表記が入るので、
シェルの二重引用符の中ではバックティックがコマンドとして実行され（`merged: command not found`）、
`$` で始まる語は空に展開される。**`<ベース>/topic-pr-body.md` に Write で書き、`--body-file` で
渡す**（`<ベース>` は `place.py base-dir --work <作業名>` が返すパス。自分を無視する `.gitignore` の
中なので、この下書きは PR の差分にも出ない）。

## 作る（§4）

```bash
gh pr create --draft --base <base> --head topic/<作業名> \
  --title "[supervisor] <種別>: <作業内容>" --body-file <ベース>/topic-pr-body.md
```

- `<base>` は「起動前の確認」でユーザーと決めた分岐元。`<種別>` は `feat` / `fix` / `docs` など、
  そのリポジトリの既存 PR タイトルに倣う。チケット番号を聞き出してあれば末尾に添える。
- **draft で作る**。仕上げが済むまで GitHub 側がマージを拒むので、途中の誤マージが起きない。
- **失敗したら 1 回だけ再試行し、それでも非 0 なら止まる。** 叩いたコマンドとエラー出力を
  ユーザーに示し、`SKILL.md` §5（権限）・§6（`TaskCreate`）に進まない。台帳 v0 と
  `topic/<作業名>` は残るので、原因が解消したら §4 のここから続けられる。
- リポジトリに PR テンプレートがあれば（`.github/PULL_REQUEST_TEMPLATE.md` など）、**その見出しを
  残したまま**下の節を足す。

## タイトルの接頭辞

supervisor が管理している PR だと一覧で見分けられるように、3 種すべてに接頭辞を付ける。

| PR | タイトル |
| --- | --- |
| topic PR | `[supervisor] <種別>: <作業内容>` |
| タスク PR（PR 本文エージェントが決め、リードが作る） | `[supervisor #<topicPR番号> task<番号>] <種別>: <件名>` |
| 残件回収 PR（[integration.md](integration.md)「却下された残件の回収」） | `[supervisor #<topicPR番号> followup] <種別>: <件名>` |

**PR タイトルを検査する GitHub Actions があるリポジトリでは接頭辞を末尾に回す。** タイトルの
先頭が `feat:` `fix:` などの型で始まることを求める job（`amannn/action-semantic-pull-request` が
その一例）では、`[supervisor]` が先頭にあると落ちる。**どういう検査なのかは実際の workflow を
読んで判断する**——§2 で `.github/workflows/` を読み、`<ベース>/brief.md` に書いてある。
回した形はこうなる。

```
fix: パーサの境界値を直す [supervisor #100 task1]
```

`#<topicPR番号>` は PR 本文エージェントに `args.topicPr` で渡る
（[workflow-script.md](workflow-script.md)「呼び出し方」）。

## 進行中の本文

台帳（[ledger.md](ledger.md)）から写して組み立てる。**`runId` は載せない**（worktree の後始末と
再実行に使う内部の値で、ユーザーが読む意味が無い）。

```markdown
## 概要

<この作業で何が変わるか。挙動の変化を 1〜3 行で>

## 全体の計画と DoD

<作業全体で達成する状態。タスクへの割り方の方針を数行で>

## タスク一覧（進行状況）

| # | 件名 | tier | 依存 | PR | 状態 | 却下した残件 |
|---|---|---|---|---|---|---|
| 1 | パーサの境界値を直す | standard | — | #101 | merged | 2 |
| 2 | エラー型を整理する | standard | — | #102 | merged | 0 |
| 3 | 一覧表を更新する | light | 1,2 | — | running | — |

状態は `pending` / `running` / `settled`（決着したがまだ取り込んでいない）/ `merged` / `blocked` /
`failed`。

## 残課題

- <回収しないと決めた残件、打ち切ったタスクとその理由。無ければ「現時点で無し」>
```

## 最終版の本文（§8）

進行中の 4 節を最新にしたうえで、次の 4 節を足す。

```markdown
## 変更による挙動の変化

- <操作 X をすると、これまでは A だったが、これからは B になる>

## 確認項目

- [ ] <操作手順> を行うと <観測できる結果> になる

## 検証結果

- <brief.md の検証コマンド一式を topic で流した結果。コマンドと結果を 1 行ずつ>
- <外形動作を確かめた手順と、観測した結果>

## 自律判断の記録

### 変更した最終目標・DoD・スコープ

- <何を・なぜ・判断材料（根拠と退けた代替案）・残課題>

### 先送り・対象外にした作業

- <何を・なぜ・次に何をすべきか>
```

- 「変更による挙動の変化」と「確認項目」は、**観測できる事象で書く**。コード内部の状態
  （変数・フラグ）は書かない。「正しく」「正常に」も使わない。
- **各タスク PR の本文と重複させない。** ここに書くのは作業全体で見たときの変化で、タスクごとの
  詳細はそれぞれの PR にある。
- 「自律判断の記録」には、ワークフローが返した `decisions` と `deferrals`、リードが
  コンフリクト解消で書いたコード（[integration.md](integration.md) §2）を集約する。
- `merged` が 1 件以上なら `gh pr ready` でレビュー可能にし、マージはユーザーに渡す。
  **1 件も無ければ `ready` を叩かず draft のまま残す**（topic ブランチも消さない。あとで続きを
  頼まれたときの足場になる。[ledger.md](ledger.md) の再開手順）。

## 更新する

`<ベース>/topic-pr-body.md` を書き直してから渡す。

```bash
gh pr edit <topicPR番号> --body-file <ベース>/topic-pr-body.md
```

**本文は毎回全文を組み立てて差し替える**（節の一部だけを書き換えようとすると、他の節を落とす）。
下書きファイルを残しておけば、前回の本文を読んで差分だけ直せる。`gh pr edit` は購読者に通知を
出さないので、更新の回数を気にしなくてよい。

ユーザーが本文に手で書き足した節が見えるときは、上書きする前にユーザーに確認する。

## このスキルが扱わないこと

**topic PR に直接付いたレビューコメントは扱わない。** PR を読んだユーザーが対処する。タスク PR に
付いたものをリードが片づける手順は [integration.md](integration.md)「却下された残件の回収」の
並びにある。
